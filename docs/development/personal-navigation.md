# 个人导航顺序

2026-10-18 用户确认的契约：管理端、员工工作台右上角「系统设置」提供
「导航栏调整」按钮，点击打开排序弹窗。允许拖动或上移/下移同级菜单，
可进入任意深度的子菜单调整，禁止跨父级移动。恢复默认清空个人顺序，
使用此时服务端的默认顺序。

只有「保存并关闭」成功后关闭弹窗并调用当前页面的 location.reload()，
保留 URL、查询条件和锚点；取消、关闭和保存失败均不刷新。
刷新会重新初始化页面内存状态，弹窗在保存前明确提示刷新行为。
请求期间禁止重复保存和关闭；读取失败可以重试，保存失败保留草稿。

## 权限和来源

- System 菜单、授权、名称、图标、显隐、层级及默认顺序仍是唯一来源。
- Workbench 在既有已发布的导航投影上排序，各布局和移动抽屉使用同一结果。
  其完整授权树、路由注册、权限检查与首页选择不应用个人顺序。
- Admin 在当前可加载菜单树上生成独立的显示菜单，授权路由注册及登录落点不变。
- 个人偏好只保存同级稳定标识：页面为原菜单 ID，Workbench 分组为 layoutKey；
  父级通过稳定键路径定位。改名不丢排序，跨父级调整不会继承旧父级排序。
- 消费端只匹配当前可见、已授权且本端支持的菜单；过期键被忽略，新菜单追加在同级末尾，
  新增项之间沿用默认顺序。偏好加载失败回退默认顺序，不阻塞登录导航。
- 这是已确认的个人展示顺序例外，替代旧规范中必须逐项保留服务端顺序的约束；
  2026-10-28 用户新增要求允许个人隐藏导航菜单，不允许自行构造菜单树或改变授权。
- zsjos:navigation-preference:query 控制设置入口与读取；
  保存同时要求 query 和 zsjos:navigation-preference:update。
  只有读取权限时可查看顺序，调整和保存按钮禁用。
- V325 仅定义权限，不授予或回补任何角色。管理员通过系统角色管理配置。

## API 与持久化

GET /admin-api/zsjos/navigation-preference?client=admin|workbench
读取本人偏好，无记录返回空 groups。

PUT 同路径及参数，示例请求：

~~~json
{"groups":[{"parentKey":"root","keys":["menu:12","menu:10"]},{"parentKey":"menu:10","keys":["menu:15","menu:14"]}]}
~~~

重置请求为 {"groups":[]}。请求和响应均使用现有 CommonResult。
不接收 userId/tenantId，不存储标签或路由。Service 从 ADMIN 登录上下文取得本人 ID，
DAL 通过框架租户上下文读取并以唯一 tenant/user/client 键幂等写入。
偏好中的键不参与授权，不能赋予任何菜单访问权。

ZSJOS 拥有新增的个人展示偏好，不复制 System 菜单与权限服务。表为
zsjos_navigation_preference，保留租户、审计和逻辑删除列；
客户端独立保存，账号跨浏览器同步，最后一次成功保存生效。
接口限制分组数、同级键数、总键数和内容长度，拒绝重复分组、重复键及控制字符。

两端组件及小型纯排序工具各自维护，不新增共享包、依赖或工作区。
同一组行为测试同时覆盖两端排序工具，防止协议分歧。

## 数据库和发布顺序

先确保 Core V324 在两个版本账本中，备份相关元数据后执行
script/sql/mysql/migrations/V325__personal_navigation_preference.sql。
该脚本通过单一失败控制路径新增空表、两个权限定义，并在结构及权限后置校验成功后
记录 V325。DDL 有隐式提交；中途失败保留空表，修复后重放。已存在错误结构会拒绝记录成功。
重复执行不改写已有偏好或角色授权。部署范围仅新增表和权限定义，不修改历史业务数据。
回滚应用代码时保留新表与用户偏好，不删除共享数据或已配置权限。

上线顺序：数据库 -> 后端 -> 两端前端 -> 管理员按需配置权限 -> 真实账号验收。
本地迁移和组件测试不代表后端已重启，也不代表目标环境验收。

## 个人导航显示（2026-10-28）
两端每行提供显示开关；隐藏父级同时隐藏其导航子树，设置弹窗仍显示所有原本可见的授权菜单，允许恢复。
每组新增可选 hiddenKeys，旧数据缺失时为空；排序与隐藏互不覆盖，恢复默认同时清除两者。
隐藏只应用于导航展示，不影响授权路由、登录落点及页面访问。全部隐藏仍可从系统设置恢复。
沿用现有本人/客户端隔离和 query/update 权限、JSON 存储，无数据库迁移。
需先部署支持 hiddenKeys 的后端，再部署两端前端；旧后端不会持久化新增字段。
