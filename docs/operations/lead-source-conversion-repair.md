# 客资来源与成交率修复（V309 开发修订 2）

本修订仅面向本地开发基线，租户 1。2026-10-10 用户已逐条确认固定清单 83 条：81 条无新媒体引流；另两条按确认的系统员工身份关联新媒体。完整业务编号、预期原值摘要在 `script/sql/mysql/tools/source_review_manifest.json`。姓名或当前岗位不是历史判断依据。

## 业务契约

销售/教务先收到新媒体引流信息而代录，业务来源是新媒体；真正本人获客才是销售/教务自拓。`submission_source_type` 是录入入口，`source_user_id` 是业务来源主体，不保证是实际录入人。实际操作人保留于可信原始事件和审计，不从负责人、快照姓名、相等编号反推。

来源解释统一为明确关联、明确无关联、不适用、待核实。明确关联必须有选择记录，且关联员工和正式提供方身份一致；`recorded=0` 不能证明有或没有关联。原生新媒体、兼职不需要自拓选择标志。姓名、组织缺失不自动否定明确关联，也不自动使用当前信息补历史。

销售/教务明确无关联均排除成交率分子、分母和明细。周期候选中的待核实来源暂停该范围比率：返回 `sourceStatus=review_required`、`sourceReviewCount`，三项转换数值为 null；金额、订单数、客单价不受影响。明细不给部分名单，旧接口报 `1900093002`。原有金额门槛和周期规则保持不变；当期 ¥980 客资仍须检查其分母影响。

无引流：清空错误新媒体关联、正式提供方类型/编号/姓名及六个来源贡献快照，标记明确无关联。保留业务来源人员、实际录入审计、负责人、计数时间、订单销售归属。

有引流：按用户确认的员工编号统一关联、正式提供方、业务来源主体和来源贡献人员。已有可信姓名快照复用；历史部门/主管无证据的保留缺失。已是新媒体且原录入入口未知的，不补造录入入口。

相关审批轮次仅修已有 `leadProfile` 的 sourceType/sourceLabel/sourceSubjectType/sourceSubjectId/sourceUserName；不改其他键或流程状态。业绩来源仅修 source_group，包含已确认错误的 frozen 来源字段；不改人员、组织、金额、时间，复购保留原分类。不补发通知、不补历史自动首跟、不修改角色菜单。

先执行 `python script/sql/mysql/tools/test_source_review_revision.py` 在独立 MySQL 中验证；确认精确目标及影响后才运行 `python script/sql/mysql/tools/media_assisted_source_repair.py apply`。前端必须先兼容新状态及 nullable 数值，再切换后端。部署期间暂停相关写入并复查新增记录，新增疑点另列确认。

修订源脚本生成：`python script/sql/mysql/tools/generate_media_assisted_source_sql.py`。本文件、生成器、revision helper、manifest 一起交付。空库不导入业务清单。V309 升级按固定客资业务编号及当前租户内关联关系定位审批轮次和业绩，不再要求与旧副本的内部 ID、关联行数、整行摘要一致；首次执行保存目标库的实际前后态。缺少清单客资、身份不符、证据不完整或保存证据后的编辑仍拒绝执行。不得重写原确认 manifest。

## 失败控制和恢复

原 V309 及本修订共享一次事务、同一异常传播路径和双账本成功登记；不使用“已有版本号”跳过结构/前态/后验。失败可能保留先前 DDL 创建的可空字段，不能宣称 DDL 可事务回滚。专用 runner 在同一连接传入当前 SQL 文件字节 SHA-256，并在迁移成功事务内更新 V309 双账本。直接 SQL 执行保留语义修订标识作为兼容值，标准 runner 随后按既有流程登记文件字节摘要。开发中修改 V298/V301/V303 的防重放保护后，必须明确审查相应文件校验变化，不批量 reconcile 其他版本。

重复执行复用固定修改后镜像；部分恢复仅允许当前记录等于最初修改前或修改后镜像。缺失/重复备份、后来编辑一律拒绝。回退先确认所有当前值仍等于修改后镜像，再按依赖逆序恢复修改前镜像；保留审计证据并审查后续迁移与版本账本，不能直接重放旧来源脚本。

V298/V301/V303 不允许在 V309 后重放；V305 订单身份修复不允许覆盖本修订。导入工具要求明确身份域、来源一致性、生成器/来源/目标/SQL 摘要，拒绝旧无元数据 payload；执行失败停止且不得报告成功。导入仍要求原有停写和精确目标授权。
