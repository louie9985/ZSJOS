# 单条客资无效状态恢复

适用范围：经用户明确确认的共享测试环境、租户 1、客资 LD202609190220。
本操作不属于 bootstrap 或版本迁移，不变更结构、版本账本、权限或其他客资。

此前 `lead_recycle_and_suspension_repair.sql` 的 A2 分支在完成回收归属时统一设置
`status='submitted'`，该客资最后修改标记吻合。用户确认其实际结果为无效；导入的
有效事件与该确认冲突，历史事件保留，本次新增独立修复审计，不伪造历史判定。

执行源为 [定向修复脚本](../../script/sql/mysql/repairs/repair_lead_invalid_20261012.py)。
依赖现有 PyMySQL、Docker、MySQL 8，以及当前 Lead、Opportunity、BusinessEvent 表。
脚本从指定容器配置读取数据库连接和凭据，不输出凭据；仅接受 test 环境标识。

顺序：锁定并检查唯一客资及唯一首购商机；检查不存在订单、申诉、待处理 Lead/Opportunity
任务及非归属绩效事实；保存受限访问的完整前镜像；在连接私有临时表中执行同一修复函数，
验证初次执行、重复执行、部分写入失败回滚和状态冲突；重新锁定并比较全部前镜像后执行事务。
临时表不修改真实业务表，失败不会遗留持久化部分状态，恢复方式是回滚后重跑。

实际写入范围：

- Lead：submitted → invalid，版本加一并记录真实修复时间和系统修复标记。
- 唯一 Opportunity：open → lost，清空下一次跟进，版本加一；lost_at 使用修复时间，
  lost_reason 明确标记业务确认的数据修复，不冒充历史流失时间或原始无效理由。
- BusinessEvent：新增唯一幂等键的 lead_state_repaired 事件，记录前后状态、关联商机和修复原因，
  operator_user_id 为空，不冒用员工身份。

Lead 的原判定时间、判定人、无效说明、字典快照、回收归属与其他字段保持原值。
缺失的历史无效原因字典值不补造。旧事件不修改，不发送新判定通知，不重算历史绩效。
提交后检查数据、非授权字段完整相等、版本递增、旧事件不变、中文 HEX 和重复执行零写入。

运行示例（证据目录必须不存在，0700 目录、0600 文件，不得提交备份内容）：

```bash
python3 script/sql/mysql/repairs/repair_lead_invalid_20261012.py \
  --container zsjos-mysql-1 \
  --evidence-dir /opt/zsjos-runtime/backups/lead-invalid-20261012-check
# 确认范围已授权后，使用另一个目录并添加 --apply。
```

提交前失败由连接回滚；提交后重复运行要求匹配修复标记及目标状态，否则拒绝继续。
提交后恢复必须重新审核并授权，先比较当前记录与 after.json，按 before.json 定向恢复
原字段并追加撤销审计；不能覆盖期间产生的新业务操作，也不能删除历史审计。
备份含业务数据，仅限受控环境访问；验收后按环境备份保留制度处理，不自动删除。

本次只修复数据库；详情时间线将非有效状态一律显示为无效的代码缺陷和旧批量修复脚本
对其他客资的影响不在本次范围内。不宣称浏览器或真实登录接口已验证。
