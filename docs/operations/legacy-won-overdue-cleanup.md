## 执行与恢复

依赖现有 MySQL 8 表、Docker 数据库配置以及已有 Python PyMySQL 环境。
凭证通过现有容器配置读取，不进入命令行或输出。环境必须解析为 `test`。

1. `prepare --plan <私有目录>/plan.json`：只读复核白名单，保存 116 条任务完整前后镜像、
   依赖摘要、计划时间和 SHA-256。目录应为 0700，计划文件由脚本以 0600 排他创建。
2. 用 `test_cancel_legacy_won_overdue_20261019.py --plan <计划>` 在相同 MySQL 引擎验证。
3. `apply --plan <计划> --sha256 <审阅摘要>`：命名锁、SERIALIZABLE 事务，先锁客资及依赖，
   严格比对快照后更新任务。仅修改 status、cancelled_at、cancel_reason、version、updater、update_time；
   取消时间使用已保存的计划时间，updater 为修复标识，不冒充业务人员。
4. `verify --plan <计划>`：独立只读连接检查完整后镜像、受保护数据、目标逾期数为零及中文 HEX。

所有命令脚本路径为 `script/sql/mysql/repairs/`，通过 `python3 -B` 执行。
任何缺失记录、后续跟进、变更后的订单或任务均拒绝覆盖并回滚。成功后重复 apply 为零变更；
与计划后镜像完全一致的部分已应用记录可跳过，实现受控恢复。无业务表 DDL，无版本台账或通知写入。
全体非目标跟进任务在写入事务内逐字段摘要比对，目标客资、订单和两类跟进记录保持摘要一致。

如需恢复，另行授权后执行 `restore --plan <计划> --sha256 <摘要>`。
仅允许任务仍与原后镜像一致时补偿恢复前镜像；后续有业务操作则拒绝。恢复不能撤回用户已看到的页面，
也不重放历史通知。计划包含业务数据，禁止提交 Git、公开展示或附在日志中。
