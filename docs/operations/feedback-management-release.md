# 需求与反馈发布说明

## V294 审批进度与催办

在 Core V155 已存在于两个版本台账的环境执行 `V294__feedback_approval_progress_urge.sql`，再部署后端及两端前端。迁移执行器按现有目录扫描纳入新文件，无须重写 bootstrap 或历史迁移。新增内容仅为轮次 `last_urged_at`、反馈页下催办按钮权限元数据、通知模板及启用租户缺失的默认站内规则；不改写历史需求、角色授权或管理员已有通知规则。DDL 不支持事务回滚，局部失败须检查实际列和两个台账后重放；已有版本标记和校验和保持不变。

管理员通过角色管理按需分配 `zsjos:feedback:requirement:urge`，并复核 `zsjos.feedback.approval_urged` 通知规则。仅提交人本人能够催办，管理端只读。共享数据库写入、真实授权和服务部署另行审批，源码交付不等于已部署。

两端催办通知点击均实时核验当前待办归属，定位消息指定的审批任务。Admin 使用现有 BPM 流程详情路由并传递 taskId；消息详情保留“查看审批任务”入口。已完成或已转交的任务不回退到其他待办。

执行 `python script/sql/mysql/tools/test_feedback_approval_urge.py` 在现有本地 MySQL 容器创建并保留独立测试数据库，验证首次、重复、部分结构、缺前置、错误列类型、版本写入失败和带旧标记恢复，以及中文 HEX 和管理员规则保护。它不修改开发业务库。目标部署前备份轮次、菜单、通知模板/规则和两个版本台账；比较目标结构及范围内元数据与隔离测试结果。回退采用旧应用或禁用通知规则，保留新增列和操作历史。

前端验证夹具使用虚构数据，运行各自独立的本地 Vite 验证端口后执行 `python frontend/workbench/test/feedback-approval-browser.py`，覆盖员工真实页面和管理端真实审批组件的桌面/移动、历史快照、错误重试、催办幂等和冷却。真实环境仍须验证授权、实际通知出站和审批消息定位。

## 交付范围

本功能由 V149、V155、V156、ZSJOS 后端、BPM 需求审批资产、Vue Admin、React Workbench 和五个站内通知场景组成。V149 固定为 `script/sql/mysql/migrations/V149__feedback_management.sql`，已部署环境通过 V155 增加“新反馈待处理”模板及租户默认规则，通过 V156 校准可能落后于历史反馈编号的日流水；V148 已被其他工作占用，不得复用。旧环境若在 V115 前已存在通用工单表，还必须执行 V154 修复工单幂等字段后再开放反馈入口。

V149 是可重复、非破坏性的前向迁移。它增加反馈表、通用工单业务类型、索引、默认表单和设置、菜单权限、通知模板及租户默认规则，不删除或重建现有业务数据。反馈、回复、审批轮次、满意度和历史快照不能通过回滚删除；需要退役时另行评审前向迁移。

V155 依赖 V149，可重复且非破坏性。它只增加一个通知模板，并为缺少该场景的启用租户增加默认站内规则；已有同场景规则保持不变，不补发历史反馈，不修改历史消息或反馈业务数据。回滚采用禁用规则，保留消息和版本记录。

V156 依赖 V149 和 V155，只新增或上调反馈日流水计数器，使其不低于现有反馈表及反馈工单中格式合法编号的最大后缀。它不下调计数器，不重编号或删除反馈、工单及消息；重复执行不会继续抬高计数器。修复后的运行时代码按业务计数器行取值，并在每次分配时以现有反馈工单最大后缀作为下限，不再使用计数器表自增主键作为业务流水。

旧环境的反馈表与工单表可能保留不同的 `utf8mb4` collation。V156 对两侧业务编号和派生反馈类型使用 binary 精确比较，不依赖表或连接默认 collation，也不会修改任何现有列的 charset、collation 或存储值。

## 发布前检查

1. 确认目标环境已登记 V147，且 Workbench 根菜单 `6735` 唯一有效。
2. 执行迁移计划和只读预检，确认反馈专用菜单 `79940-79957`、反馈权限、表单 marker、字典 ID 及路由不存在身份冲突。`79911-79912` 归 V148 公告动作按钮所有，`79910` 已由 V158 退役，`79913` 归 V158 公告阅读按钮所有，原通知公告入口回到菜单 `107`；`79920` 归 V150/V151 兼职权限所有，V149 不得复用。
3. 校验 `script/bpm/manifest.json`；需求流程 Key 必须为 `zsjos_feedback_requirement_approval`，资产版本 `1.0.0`，任务 Key 为 `departmentLeaderReview`、`chairmanReview`。
4. 备份目标数据库并记录当前租户套餐、反馈相关权限和通知规则。真实迁移、流程发布和权限分配必须走发布审批。
5. 构建并验证后端、Admin 和 Workbench 产物；确认部署版本均来自同一已评审提交。

## 发布顺序

1. 依次执行 V149、V154、V155、V156；V154 对结构已完整的工单表只登记版本，不改写工单数据，V155 不修改反馈业务行，V156 只校准反馈日流水计数器。运行 `script/sql/mysql/verify-bootstrap.sql` 中全部 V149、V154、V155、V156 检查，确认工单幂等字段、通知模板、逐租户规则、计数器不落后于历史编号及版本记录完整。
2. 部署后端，确认 ZSJOS 与 BPM 模块启动及反馈接口注册正常。
3. fresh bootstrap 环境由管理员复核已初始化的未发布需求审批模型；已有环境按 `script/bpm/manifest.json` 导入模型。两种路径都由管理员发布并启用，不启用应用自动部署。
4. 在“反馈设置”检查四张默认动态表单、需求审批开关和已发布流程绑定。
5. 为需求、BUG、技术支持分别配置至少一名分派负责人；未配置的入口会保持“暂未开放”。
6. 通过服务端菜单/按钮权限分配页面和操作权限，并验证授权、未授权及本人数据隔离。
7. 发布 Vue Admin 与 React Workbench，检查 `/zsjos/feedback` 及 Admin 四个子菜单。

不得跳过第 1-5 步提前开放员工创建入口。需求审批开启时，现有 `boss` 角色必须恰好解析到一名启用用户；否则提交会被业务校验拒绝。提交人部门负责人缺失时流程跳过第一节点，但不会跳过董事长终审。

## 发布后验证

- 分别创建需求、BUG 和技术支持，确认编号格式与租户/日期/类型日流水隔离；另用计数器自增主键不等于 `1`、计数器落后于历史编号的场景确认下一编号仍唯一且连续向前。
- 覆盖需求两级审批、负责人缺失跳过、驳回后同编号重提，以及董事长配置异常。
- 覆盖分派、改派、双方回复、完成、完成后回复、未读和五类通知接收人；BUG、技术支持及免审批需求提交后立即通知当前有效分派负责人，审批需求仅在最终通过后通知，同一审批轮次不得重复通知。
- 覆盖满意度只能发起和提交一次，评分必须为 1-5，结果只出现在原反馈详情。
- 在桌面和移动宽度检查卡片、筛选、加载更多、表单和详情；验证加载、空、错误、重试和未授权状态。
- 确认普通工单接口只返回 `GENERIC`，不会暴露 `FEEDBACK` 记录。

若应用部署失败而 V149 已成功执行，可回退应用版本并保留新增结构。不要删除反馈表或重写 V149；流程、数据或权限修复必须使用单独评审的前向变更。
