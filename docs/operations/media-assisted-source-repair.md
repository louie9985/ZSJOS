## 执行与恢复

前置 V308 双版本账本、既有 LONGTEXT 备份表和事务型目标表。顺序 V308 → V309 → 新后端。
生成源为 `script/sql/mysql/tools/generate_media_assisted_source_sql.py`，产物为
`script/sql/mysql/migrations/V309__media_assisted_source.sql`；生成与执行分离。
现有模块清单自动发现编号迁移，两个 schema 文件同步定义新列。

只读：`python script/sql/mysql/tools/media_assisted_source_repair.py audit`。
本地应用：同工具 `apply`，默认现有本机 Docker 开发库。远程/生产必须另行核对目标和授权。
SQL 使用 UTF-8/utf8mb4，预检、变更、后验及双账本共用失败传播过程；客户端遇错即停。
DDL 隐式提交，因此失败时可能已存在新列，不能以事务回滚或版本标记代替结构检查。

空库只加列、登记成功，不插入业务数据；固定清单部分存在、归属证据冲突、备份缺失或后续
受保护字段编辑均拒绝。重复运行和带账本的部分恢复使用原始镜像，不重取当前人员或组织。
发生失败先检查列、两个账本及镜像。恢复必须匹配已保存的完整后镜像，按 table/row 精确恢复
前镜像中的字段；保留备份证据，不直接删除版本标记，先审查新写入及后续迁移依赖。
旧 V298/V301 不得在 V309 后当作“同步工具”重放，否则可能重新按旧来源规则归类。

后端切换前旧进程仍可能产生旧来源记录，部署窗口应在切换后审计新增关联录单；不得扩大本次
固定历史清单去静默覆盖新记录。此次不重启服务、不部署生产、不补发通知。
