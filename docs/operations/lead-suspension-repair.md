# 挂起恢复后的成交拦截修复

恢复、转派重启判定和判有效必须在同一次数据库更新中清空 `suspended_at`。
`LeadMapper.updateClearingSuspension` 使用显式 UPDATE SET NULL；不能仅依赖
`setSuspendedAt(null)` 和默认忽略空值的 `updateById`。成交接口继续执行原有
状态、归属和挂起校验。回收与申诉恢复已有显式清空路径，保持原逻辑。

## 历史残留修复边界

代码更新不会自动修复已存在的残留。本次报告的测试环境客资为
`KZ202610012135440007`，租户为 1。操作前必须通过实际测试环境连接核实
当前主状态、归属、挂起时间、恢复及有效判定事件，以及关联商机状态。
用户报告的历史时间只作为核对依据，不能替代当前数据库检查。

仅当仍为有效、已归属且事件证明确已恢复时，才允许清除此记录的
`suspended_at`。执行者应保存最小前镜像，在事务中锁定记录，并使用租户、
业务编号、未删除、当前状态、归属及旧挂起时间作为更新条件；影响行数须为 1。
复读确认挂起时间为空，状态、负责人及商机未被改写，再提交。重复执行时
已为空则无需更新；前置状态变化则停止。不得重新判有效、改权限或批量清空。

恢复前镜像只适用于确认没有后续业务变更的情况；不能在已成交后盲目恢复
挂起时间。历史挂起/恢复业务事件保留，不修改已有时间线。

## 验证与上线

`LeadQualificationServiceImplTest` 验证恢复、转派、判有效调用显式清空方法；
`LeadSuspensionMapperTest` 用真实 MyBatis-Plus/H2 映射检查落库与事务回滚、
其他记录及逻辑删除记录保持不变。H2 测试不等于测试环境 MySQL 或已部署接口验收。

后端部署后需用有权限的用户验证成交入口；新建真实订单仍应由正常业务流程执行。
本地源码修复、测试环境历史数据修复和后端部署分别记录交付状态。
