## 执行、重跑与恢复

Python 使用环境中已有 `pymysql/openpyxl`；不新增依赖。认证只在进程内读取现有本地容器密码，
不放在参数、计划或日志中。连接设置 utf8mb4 和上海业务时区，写入后逐条检查中文 `HEX()`。

示例参数中的路径均为仓库外受控目录：

```powershell
python script/historical-student-import/import_students.py prepare --source <源文件绝对路径> --identity-confirmations <私有同人确认JSON> --database ruoyi-vue-pro --actor-username <现有执行账号> --plan <新计划绝对路径>
python script/historical-student-import/import_students.py apply --source <源文件绝对路径> --identity-confirmations <私有同人确认JSON> --database ruoyi-vue-pro --actor-username <现有执行账号> --plan <计划绝对路径> --sha256 <预检输出摘要> --result <新结果绝对路径>
python script/historical-student-import/import_students.py verify --source <源文件绝对路径> --identity-confirmations <私有同人确认JSON> --database ruoyi-vue-pro --actor-username <现有执行账号> --plan <原计划绝对路径>
```

预检只读，输出逐行目标映射、异常及计划摘要。提交要求完整计划文件摘要；在同一事务内重新锁定、
校验服务器 UUID、数据库、目录/人员配置和身份，不使用过期预检。联系方式沿用现有 claim 行锁，
同批加数据库命名锁；不创建持久锁表。创建人员、占用、日计数器、课程服务、协作组、历史记录及
新班级、业务事件在同一 InnoDB 事务内提交，失败回滚，不执行 DDL。没有班级名称/班主任组合
唯一索引时，使用 REPEATABLE READ 下的目录锁定读（包含插入间隙）防止缺失组合并发重复创建。
目录查询显式按 ID 排序，避免执行计划改变读取顺序导致计划摘要误报。

`student_historical_import` 业务事件按文件摘要、工作表、原行号幂等，附内容指纹。
v2 保留旧版事件指纹的只读重放识别：已经导入的行直接列为已处理，不套用新规划师选择、
不创建新班级、不调整旧服务。v1 计划不能以 v2 写入，须重新预检；v2 新班级另外记录
`student_historical_class_created` 事件，组合幂等键和服务创建处于同一事务。
v3 继续识别 v1/v2 已提交事件，但旧版本计划必须重新预检。允许历史备注姓名复用时，人员档案
原姓名和联系方式不变，课程服务姓名使用表中姓名；业务来源中记录
`identityNameMatch=historical_student_suffix` 及 `storedIdentityName`，明确复用依据。
预检及事务内最终身份复核共用同一规则，避免预检通过但实际写入仍按旧规则拒绝。
v4 扩大为有明确身份依据的同类情况，并把确认相同的已有服务单列为无操作结果；继续保留旧事件，
原档案姓名和联系方式不变。新的报告为仅供复核用途，`reportOnly=true` 文件禁止写入执行。
v5 增加用户逐条确认的四条同人映射，必须携带仓库外确认文件，不写死人员 ID，不扩展为通用昵称
或姓名前缀猜测；确认不绕过联系方式唯一归属。细节见身份核实说明。
相同原计划重试只核验已提交服务，返回零新增，不补写或覆盖；内容、映射或人员状态发生未预期变化
时停止并要求重新预检。提交后结果文件写入失败时，不凭文件缺失认定数据库未提交，应通过事件
和 `verify` 恢复判断。跨文件或改过文件的幂等不依赖行号复用，必须重新审批业务决策。

计划保留既有人员的导入前必要状态；另保留本地写入前后的摘要证据和验证库。提交后的撤销是另一项
会影响具体业务记录的受控操作，不能擅自删除新人员（可能已被后续业务引用）、服务或审计事件。

`execute_local.py` 审计执行器也必须显式提供 `--reviewed-plan` 和 `--sha256`，不再固定要求
423 条或复用旧异常数量。它核验新计划后保存写前摘要、执行并检查旧班级/服务和无关表不变。
v5 同时要求 `--identity-confirmations`，测试入口 `verify_mysql.py` 也传同一个已审核确认文件。

列依次为：异常原因、姓名、手机号、课程规格、班级、规划师、待确认内容、原表行号、处理意见。

## 验证

`verify_mysql.py` 创建独立且保留的 MySQL 8 验证库，从本地复制适用数据（生成列由数据库计算）。
验证源行数分区、完整导入、注入失败后的全部行/计数器回滚、恢复执行、原计划重放零变化、
身份冲突拒绝、旧班级/服务/协作组/联系/事件不变、销售目录不变、班主任归属、教学隔离和中文 HEX。
分别构造未导入本批数据的验证库（复制时排除本批创建行，不在源库执行删除），以及保留所有
旧版导入事件的混合验证库。覆盖同名不同班主任拆班、同组合复用、歧义/失效/无资格规划师拒绝、
同组合重复班级拒绝、建班与服务共同回滚和旧事件保持原样。源业务库仅执行 SELECT，前后逐表摘要
验证无变化，不删除验证库。

数据库结果不等于在线账号验收；本地服务不可用时不擅自启动服务，应明确报告接口/页面未验收。
