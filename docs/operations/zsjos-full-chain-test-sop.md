# ZSJOS 全平台业务功能链路测试 SOP

## 1. 目标与范围

本 SOP 用于验证 ZSJOS 在三端、后端、数据库和外部依赖之间的完整业务闭环。范围以现有菜单覆盖矩阵、角色权限矩阵、生命周期模型和 API/运维契约为准。

覆盖运行面：

- Vue Admin：管理员配置、全局管理和审批配套页面。
- React Workbench：员工业务、BPM 统一入口、任务和工作台页面。
- Partner H5：兼职主体认证、客资、返现、提现、消息和反馈。
- 后端/API/DB/BPM：业务状态、快照、权限、租户、审计、流程和持久化结果。
- System、Infra、通知、Quartz、Redis、文件、支付和媒体大屏：只验证 ZSJOS 实际依赖的公共契约。

不包含：生产数据操作、未经确认的批量清理、真实资金划扣、上游模块不被 ZSJOS 使用的独立全量回归。

## 2. 测试准入

测试负责人在开始前记录环境编号、部署版本、分支/提交、数据库迁移版本、租户、三端地址和依赖状态。账号、Token、密码和个人数据不得写入仓库文档或缺陷描述。

准入检查：

1. Admin、Workbench、H5 可访问，后端健康检查和接口文档可用。
2. 测试租户、部门、岗位、角色、字典、产品/SKU、BPM 流程和文件目录已准备。
3. Redis、Quartz、通知、WebSocket、支付沙箱和媒体大屏访问策略有明确状态；不可用依赖必须标记为阻塞或降级验证。
4. 业务时区为 `Asia/Shanghai`，测试时间、编号和任务提醒可复现。
5. 数据库只读核验账号可用；禁止用生产账号和生产个人数据。

## 3. 角色与端矩阵

至少准备 `super_admin`、`system_administrator`、`sales_manager`、`sales_specialist`、`part_time_partner`、`enrollment_manager`、`enrollment_specialist`、`finance_manager`、`finance_specialist`、`quality_manager`、`quality_specialist`、`boss`、`study_planner`、`content_director`、`new_media_operator`、`filming_editor`、`delivery_manager`、`normal_user` 和一个无 ZSJOS 菜单角色。

每个角色验证：服务端菜单、直接路由、按钮权限、接口拒绝、列表数据范围、对象读写/动作权限、租户隔离及与 BPM 候选人的独立校验。角色授权只能按服务端 permission 和关系数据判断，不按角色名称在前端推导。

## 4. 执行阶段

### P0 冒烟

登录/退出、菜单加载、核心接口、客资提交、分配或接单、订单提交、BPM 审批、支付结果、报名完成和学员服务关系建立至少完成一条闭环。

### P1 核心回归

执行完整客资、订单支付审批、报名履约、学员服务、媒体生产和 Partner/财务链路；同时覆盖权限、租户、状态机、快照、通知、文件、异常、重复请求和并发。

### P2 全功能回归

逐项覆盖菜单矩阵中的页面和管理能力，包括规则配置、筛选、工作计划、申诉、导出、人员/兼职、审计、返现/提现、消息、反馈、资产、维护模式和强制表单。

### P3 兼容与体验

检查桌面/移动宽度、浏览器刷新和直达、loading/empty/error/retry/unauthorized、长文本、附件、下载、性能和文案。

## 5. 通用验证规则

每个用例必须覆盖适用的成功、必填/格式/边界、重复提交、非法状态、失效字典/产品/流程/文件、功能权限、数据范围、对象权限、批量混合授权、租户隔离、乐观锁和异常恢复。

业务结果以 API 和持久化业务记录为准；WebSocket 只验证提示和刷新触发。历史记录使用存储的字典标签快照，用户可见客资编号使用 `leadNo`，BPM 任务和历史使用 BPM 公共能力。

## 6. 缺陷与发布门禁

缺陷必须记录复现步骤、角色/租户、业务编号、接口或页面、实际/预期结果、影响范围、证据、日志摘要和回归范围；不得记录密码、Token 或完整敏感请求体。

发布条件：P0 100% 通过；P1 无未关闭阻断/严重缺陷；至少一条核心链路闭环；权限、租户隔离、对象授权无高风险问题；BPM、支付回调、通知、异步导出、定时任务和数据库关键状态均有证据；失败项有缺陷编号和复测结论。

## 7. 工具与验证命令

```text
mvn -f backend/pom.xml -pl yudao-module-zsjos -am test
cd frontend/admin && pnpm ts:check && pnpm lint && pnpm build:local
cd frontend/workbench && npm test && npm run typecheck && npm run build
cd frontend/h5 && npm run build
```

自动化结果不能替代真实环境的权限、BPM、支付、文件、通知和浏览器验证。涉及数据库、共享服务或资金动作时，先按仓库风险规则确认具体目标、影响和恢复方式。

## 10. 测试数据与证据规范

### 9.1 数据准备原则

测试数据必须属于专用测试租户或明确隔离的测试空间。优先通过正式页面/API 创建；数据库只用于只读核验。不得写入真实个人信息、生产账号、密码、Token、支付密钥或完整敏感请求体。

建议编号：

- Person：`T-P-YYYYMMDD-序号`
- Lead：记录并展示服务端生成的 `leadNo`
- Order/Payment/Registration：使用服务端业务编号，不自造替代编号
- 测试账号：`T-{角色编码}-{序号}`，实际用户名和密码只放密码管理工具
- 缺陷证据：使用测试编号、业务编号和脱敏摘要关联

### 9.2 测试数据包

| 数据组 | 最小内容 | 验证点 |
|---|---|---|
| 租户组织 | 两个测试租户、部门树、岗位、角色 | 租户隔离、直属/子部门范围 |
| 账号 | 角色矩阵中的账号及一个无菜单账号 | 菜单、功能、BPM候选人、对象责任 |
| 字典 | 客资来源/分类、订单/履约/账号等实际配置项 | code/value、label snapshot、失效项 |
| 产品 | SPU/SKU、价格、规则版本和禁用样本 | 产品引用、价格快照、失效错误 |
| BPM | 订单、履约、资产所需流程定义和版本 | business key、候选人、通过/拒绝/驳回 |
| 客资 | 新客、重复客、已拥有、抢单池、公海、申诉样本 | 查重、分配、跟进、流转和权限 |

### 9.3 数据创建与清理

创建顺序遵循依赖：租户/组织/账号 -> 字典/产品/SKU -> BPM/通知/规则 -> Person/Partner/Lead -> Opportunity/Order/Payment -> Registration/ServiceRelation -> 学员/媒体/任务/外围记录。

清理不是默认步骤。需要删除、批量重置、回滚支付或修改共享权限时，先列明准确对象、行数/租户范围、关系顺序、备份或恢复方案。优先使用业务撤销、失效或新建隔离数据；保留审计和历史证据。

### 9.4 数据库只读核验

只读取与业务编号相关的最小集合，重点检查：

- tenant、逻辑删除、创建/更新时间和操作者
- Person/Lead/Order/Payment/Registration/ServiceRelation 的主外键和状态
- `lead_no`、订单号、支付号、流程实例 ID 和 business key 的关联
- 字典 code/value 与 label snapshot
- 订单项、支付分配、账户余额和只追加账本守恒
- BPM 引用、业务审批轮次、状态事件幂等结果
- 通知事件键、站内消息、业务事件和审计记录
- 文件临时/绑定状态及业务对象归属

禁止在证据中输出全表、完整手机号、身份证号、支付密钥、Token 或密码。SQL 只保留脱敏条件、结果摘要和执行时间；不把数据库脚本作为清理工具。

### 9.5 证据包结构

每个 P0/P1 用例至少保留：

1. 操作前页面或请求摘要。
2. 关键操作后的页面截图或 API 响应摘要。
3. 业务编号、角色、租户和时间。
4. 必要的数据库只读结果、BPM 任务/实例结果或通知结果。
5. 若失败，附错误码、脱敏日志摘要、复现次数和缺陷编号。

建议目录命名：

```text
evidence/<release>/<date>/<case-id>/<role>/<tenant>/
  before.png
  action.json
  response.json
  after.png
  db-summary.txt
  defect.md
```

真实 Token、密码和敏感附件不得放入上述目录或 Git。截图应裁剪浏览器地址栏中的敏感参数，响应文件只保留必要字段。

### 9.7 缺陷分级与复测

`阻断`：无法登录、租户串数据、核心链路无法闭环、资金重复记账或严重越权；`严重`：核心业务状态错误、审批/支付/履约结果错误；`一般`：非核心功能失败或可绕过问题；`轻微`：文案、布局和体验问题。

复测必须使用原角色、原租户和可复现数据，确认修复后业务状态、数据库、BPM、通知和审计无回归。关闭缺陷前重新执行受影响的 P0/P1 用例及对应跨切面用例。
