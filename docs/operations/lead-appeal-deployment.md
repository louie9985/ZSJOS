# 客资三级申诉发布说明

当前推荐资产为 `script/bpm/zsjos_lead_appeal_review/2.0.0/process-model.json`，流程 Key 固定为 `zsjos_lead_appeal_review`。发布前必须运行 `python script/bpm/validate_manifest.py` 并核对清单 SHA-256。新环境须由管理员导入模型；已有环境打开现有模型并更新为 SIMPLE 后由管理员审核和发布，不重复导入同 Key 模型，不启用全局自动部署。

执行顺序：

1. 在受控环境先执行增量迁移 `script/sql/mysql/migrations/V015__lead_three_level_appeal.sql` 和 `V016__complete_lead_notify_templates.sql`。确认 V022 已集成且 V023、V024、V025 已按序执行后，再执行 `V026__lead_appeal_reviewer_snapshot.sql` 并运行 `script/sql/mysql/verify-bootstrap.sql`；缺少 V022 的环境不得执行 V024 或 V026。
2. 为每个租户配置恰好一名启用的 `boss` 角色用户；迁移只在角色编码缺失时创建角色，不自动分配账号。
3. 在 Admin 进入“工作流程 → 流程管理 → 流程模型”。新环境导入模型后配置表单；已有环境打开现有模型并更新为 SIMPLE，流程标识保持 `zsjos_lead_appeal_review`，流程名称填写“客资申诉复核”，设为不可见、发起范围为全员，并指定流程管理员。
4. 在“表单设计”选择“客资申诉流程关联信息”。该表单只读，只展示 `appealId`、用户可见的 `leadNo`、`roundNo` 和 `reviewStage`；内部流程变量仍保留 `leadId` 用于业务关联。申诉仍由 ZSJOS 工作台提交，不从 Admin 通用流程入口手工发起。
5. 无同 Key 模型时使用“导入模型”；已有模型先导出原配置，再按统一资产说明用 `prepare_model_update.py` 合并 SIMPLE 结构，通过 `/admin-api/bpm/model/update` 保存。保留已有表单、分类、管理员和发起范围，核对后单独发布。
6. 保存并发布，确认流程 Key、任务 Key `appealReview` 和多人或签（任一人通过或驳回即结束）配置正确。

迁移只增加申诉字段、索引、状态字典、菜单、授权、系统技术表单和审批人快照，不删除或重写业务数据。审批人按照提交时的客资负责人及其组织关系解析并冻结；第一轮从负责人所在部门开始逐级向上查找最近的启用主管账号，该账号还必须持有销售主管申诉审批权限，且不能是客资负责人本人。后续客资转交不改变已提交轮次。已存在申诉历史的环境不回填快照，只有快照为 `NULL` 的历史待办以 BPM 实际 assignee 为准；非空但无效或为空数组的快照会拒绝审批。已存在申诉历史的环境中，幂等键列允许历史空值，MySQL 唯一索引仍允许多条空值；后续请求必须携带非空幂等键。若流程定义缺失或审批人策略不匹配，提交前校验返回可识别错误；同步 BPM 启动失败仍整体回滚并记录原始异常。发起人自动推进发生在事务完成回调时，其失败不能视为原提交已回滚，应按下述流程状态核查。回滚采用禁用菜单、技术表单和流程定义，保留申诉与业务事件审计数据，不通过删列恢复。

申诉无时限、无自动升级、最多三轮；第二和第三轮均由提交人手动重新提交。


## 审批人契约漂移修复（2026-10-08）

本次没有表结构或编号 SQL 迁移。标准 2.0.0 模型资产已经使用 `candidateStrategy=35`；
实际部署模型如使用 `candidateStrategy=60`、`candidateParam=${coll_userList}`，与业务提交的
`PROCESS_START_USER_SELECT_ASSIGNEES[appealReview]` 不匹配。不要为所有新申诉补一个旧表达式变量。

发布前导出现有模型，保留租户维护的表单、管理人、发起范围、或签规则和节点标识。
只将 `appealReview.candidateStrategy` 改为 35，将 `candidateParam` 清空；核对生成 XML，
经管理员确认后发布新版本。旧定义的 XML、历史和实例不能覆盖。发布会禁用旧定义的新发起资格，但不会挂起其运行实例；恢复允许这种旧定义停用状态，仍要求实例和任务处于活动状态。新应用会拒绝仍使用错误策略的模型，
因此应协调模型与应用发布时间，并在恢复业务前验收新申诉。仅保存草稿不改变当前生效定义。

### 旧实例预检查

`script/bpm/appeal_recovery_preflight.py` 仅使用只读事务查询一个指定租户和客资，输出定义 XML
SHA-256、实例/任务关联、冻结审批人、作业数量与阻断项。使用已经配置凭证的 MySQL 客户端：

```bash
python3 script/bpm/appeal_recovery_preflight.py \
  --tenant-id 1 --lead-no KZ202610081727330056 \
  --mysql-command 'mysql --defaults-extra-file=/path/to/restricted-client.cnf' \
  --database zsjos
```

`CANDIDATE` 仅代表 SQL 预检查通过，不能视为执行授权。脚本仅接受第一轮销售主管申诉；
它对显式菜单授权做保守检查，不替代 System 权限 API，也不反序列化 BPM 内部 Java 数据。
租户、业务编号必须由操作人明确指定，不能从目录名或发布文件名推断环境。

### 受控恢复边界

`BpmStartUserTaskRecovery` 是 BPM 模块内的恢复辅助类，没有 Spring Bean、HTTP、定时或启动入口。
必须由经审阅的一次性运维调用接入**现有应用的 ProcessEngine、System API 和同一个 Spring
PlatformTransactionManager**。不得启动第二个连接共享库且携带调度器的应用来调用它。
当前交付包含辅助类和隔离测试，不包含已授权的共享环境执行入口。

调用方必须先获得指定实例的操作授权，重新锁定/核验业务申诉的未裁决状态、轮次、流程引用与冻结
审批人；将其与 BPM 已保存的指定审批人集合逐一对齐。调用方不得自行传入任意审批人或权限来替代
业务核验。`Request` 的 operatorUserId 是实际获准操作的 ADMIN 用户，须启用并具有 `bpm:task:update`；
审批人须启用并仍具有该轮次对应权限。业务锁与恢复事务的最终集成需要在目标环境的受控入口中验收。

辅助类要求在原事务/afterCompletion 之外调用，并使用引擎事务管理器开启恢复事务。它核验精确
XML 指纹、租户/实例/业务 Key、仅有的发起人任务、SYSTEM 自动通过状态、无审批任务历史和无作业；
冻结审批人与发起人相同或任一状态不匹配都会停止。它只为旧实例写入兼容变量，保留原自动审批人
快照和理由，新增带实际运维操作者的恢复评论，然后完成发起人任务。提交前必须出现与冻结审批人
完全一致的 `appealReview` 待办，否则整次恢复回滚。原申诉号、轮次、业务状态和流程定义不变。
同一恢复在主管待办仍存在时重复执行为无操作；已经裁决/结束等其他状态拒绝继续。

禁止直接修改 ACT_* 表、删除审计、把申诉直接改成已裁决，或重新调用申诉提交生成第二轮。
恢复命令不会重发原申诉通知；任务创建可能触发现有 BPM 通知监听，须在目标演练中核对通知副作用。
后续主管真实裁决不属于恢复命令。

### 验证与恢复限制

隔离测试使用 Flowable 8、H2、Spring 事务和项目自定义任务行为：复现缺变量推进失败、保留已写入的
自动审批状态，覆盖原实例推进、审计保留、重复无操作、租户/权限/快照冲突及后置检查失败整体回滚。
这不替代目标 MySQL、完整 Spring 监听器、HTTP 或浏览器验收。

正式执行前保存受限的业务/BPM 前像与模型导出，先演练后执行指定的一笔，再核对页面可见性、权限
隔离、详情空字段、任务归属和通知。成功推进后的回退不能靠删除新任务或变量实现；若出现新异常，
停止并基于保留的历史制定 BPM 补偿操作，不得重置共享数据库。另一笔同类申诉必须单独列入操作范围。
