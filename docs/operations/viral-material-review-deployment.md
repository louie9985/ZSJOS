# 爆款账号/内容拆解审核部署

爆款账号（`viral_account`）与爆款内容（`viral_content`）走素材库通用审批链路 `MaterialService.submit`，服务端按素材类型固定映射流程 Key，不再读取或维护素材类型上的 `bpmProcessDefinitionKey`。两套可导入的 SIMPLE 资产会创建 BPM 自定义表单；导入后仅需在 BPM 节点选择当前租户有效的审核角色。多人匹配同一角色时或签——任一人通过即通过，任一人驳回即驳回。

本流程审核节点直接在 BPM 设计器里指定角色（`ROLE` 候选策略），候选人由引擎按角色解析，后端零改动。两个模型由管理员在 BPM 后台人工创建、发布并启用，不使用全局自动部署。由于角色在模型内按角色 ID 绑定，新环境、新租户需在目标环境的 BPM 后台绑定本环境的角色。

> **资产与线上口径的差异（2026-09-26 起）**
>
> `script/bpm` 下的资产是**可移植模板**：审批节点用角色（策略 10）加 `candidateParam: "0"` 占位符，
> 导入后必须在 BPM 里绑定当前租户的角色。校验器 `validate_manifest.py` 只允许 `35`/`60`，
> 外加给角色模板的 `10`，**不允许在资产里写死用户编号**，因此资产无法如实记录一个用户绑定。
>
> 租户 1 的线上定义目前**按用户绑定**（策略 30，`candidateParam: "12"` = 程伟），不是角色绑定。
> 这是 2026-09-26 的一次既定改动，已在租户 1 验证有效。**照资产导入新环境得到的是角色模板，
> 不是租户 1 的现状**；两者行为不同，不要直接比对。详见 `tools/viral-bpm-20260926/CHANGE.md`。

发布前按顺序完成：

1. 确认 V194 已在目标环境执行，`zsjos_material_type` 已存在租户级 `viral_account`、`viral_content` 两行，且素材审批分类 `zsjos_material` 由 `MaterialTenantInitializer` 在应用启动后已为该租户创建、启用。缺少任一前置的环境不得继续发布。
2. 确认目标环境存在启用中的审核角色（租户 1 为董事长角色，`id=3031`），且该角色下有成员；该角色成员即审核节点的或签候选人。角色策略按 `system_user_role` 解析候选人，用户被停用或已逻辑删除时会从候选中剔除，因此角色里残留的停用账号不构成死待办。总监岗位补齐前不改绑，补齐后在第 4 步的模型里将审核节点角色从董事长改为总监并重新发布，不动流程结构与流程标识。
3. 在 Admin 的“流程模型 → 导入模型”分别导入 `script/bpm/zsjos_viral_account_review/1.1.0/process-model.json` 和 `script/bpm/zsjos_viral_content_review/1.1.0/process-model.json`。导入会在当前租户创建并绑定内嵌 BPM 表单；选择已启用的 `zsjos_material` 分类，两个模型设为不可见并指定流程管理员。1.1.0 的审批节点 id 与线上定义一致（`Activity_0d6b214f…` / `Activity_fb10be5a…`），1.0.0 用的是占位的 `viralReview`，两者不可混用。
4. 两个模型使用相同的三节点结构：发起人（编导） → 爆款审核（userTask） → 结束。审核节点参数：节点名称填“爆款审核”，不写“董事长/总监”以免误导；审批人来源选“角色”，绑定第 2 步的角色；多人审批方式选“或签（一人通过或拒绝）”；审批意见必填打开；关闭“发起人自选审批人”。提交时 `startUserSelectAssignees` 保持为空，候选人由引擎按角色解析。资产内 `candidateParam` 固定为占位符 `"0"`，导入后必须在设计器里替换为本租户的角色编号。
5. 模型使用“流程表单”，导入时自动创建并关联内嵌表单。在 BPM 表单设计器可调整布局；保留 `materialNo`、`materialVersionNo`、`materialTitle`、`materialSummary`、`materialContent` 字段名及只读权限。字段由已保存素材版本填充，动态字段和附件的完整查看仍使用素材详情。不可把审批表单编辑作为素材版本修改入口。
6. 发布两个模型为新流程版本并保持启用。运行中的旧实例保留原定义并继续走完，不迁移、不重启、不改写在途实例。
7. 不在“素材库 → 类型与模板”配置审批流程。`viral_account` 和 `viral_content` 的流程路由由服务端固定契约负责，页面不提供这两个类型的业务绑定入口。
8. 用受控素材验证：编导提交一条爆款拆解草稿后，审核角色成员产生待办；任一成员通过则该轮通过、素材版本生效；任一成员驳回则该轮驳回并写入必填审批意见；确认提交人不出现选审批人步骤。审核人解析结果落在 `ACT_RU_TASK.ASSIGNEE_`，**不写 `ACT_RU_IDENTITYLINK`**，排查时按 `ASSIGNEE_` 查，不要查身份链接表。

先部署支持 `importForm` 的 BPM 后端及固定映射的素材服务，再导入 JSON；旧后端会忽略内嵌表单，不能完成一键导入。导入需要 `bpm:model:import` 与 `bpm:form:create` 权限；表单和模型在同一事务创建，重复 Key 会在创建表单前拒绝。审批角色不随文件跨租户复制，发布前必须在 BPM 配置，不能自动通过代替配置。

已有相同 Key 时先导出备份，使用 `prepare_model_update.py` 更新节点树，保留现有表单或在 BPM 表单管理中新建并关联；更新接口不会执行 `importForm`。不要删除旧模型或实例以绕过重复 Key。停止新申请可停用定义；保留素材版本、轮次和历史。业务键继续为 `material-version:{materialVersionId}`，重提新增审批轮次，不改写已保存快照。没有数据库结构变更，非爆款类型的历史绑定保留兼容；内容批审和交付延期不在本次改动范围内。

改审核人可以完全走 Admin API，不必重新编译：`PUT /admin-api/bpm/model/update` 提交模型导出并替换节点树，再 `POST /admin-api/bpm/model/deploy` 发布为新版本。走这条路 `ACT_RE_PROCDEF.CATEGORY_` 会保留 `zsjos_material`，`bpm_process_definition_info` 扩展行也会自动生成，不需要 SQL 兜底 —— 这一点与用 standalone Flowable driver 直接部署不同（那条路 category 不落盘，必须手工补）。

## 拆解页面仅显示封面时的模板恢复

两类拆解页面的右侧三栏来自素材类型的 `currentSchema.fields`。类型存在不代表模板可用：
`current_schema_version_id` 引用缺失记录时，接口会返回空模板。前端对此显示“拆解模板不可用”，
不再保留可保存的空表单；独立拆解页的重试会重新获取类型和字典。

默认类型初始化会检查模板记录是否实际存在。失效引用优先重新关联已有已发布版本；
仅在没有可见模板版本时使用既有服务端默认字段重新初始化。草稿和归档版本不会因打开页面而发布，
有效模板不会被覆盖。此行为同时服务 React 拆解页和 Vue 素材管理，接口字段结构不变。
这不是历史模板恢复工具；已有自定义模板或历史素材快照丢失时，应从经审查的备份恢复。

尚未部署上述检查的环境，可在批准共享库写入后执行
`script/sql/mysql/repair-viral-template-references.sql`：仅清除租户 1 两类爆款的失效引用，
且要求该类型完全没有模板版本或素材记录。先备份两行类型数据，再执行脚本，随后打开拆解页，
由现有类型列表初始化逻辑重建默认模板；最后确认已发布模板具备三个 section，
通过 UTF-8 客户端核对中文标签及其 HEX。脚本不属于编号迁移链，不改权限、字典或历史迁移校验和。
