# 爆款账号/内容拆解审核部署

爆款账号（`viral_account`）与爆款内容（`viral_content`）走素材库通用审批链路 `MaterialService.submit`，提交时按素材类型上绑定的 `bpmProcessDefinitionKey` 启动流程，仅校验流程分类为 `zsjos_material`、已发布且未挂起，不校验节点结构与审批层级。业务规则为编导提交后单级审核：审核人固定为角色，当前总监岗位缺失，暂由董事长角色代理，将来总监补齐后仅在 BPM 界面改绑角色，流程结构不变。多人匹配同一角色时或签——任一人通过即通过，任一人驳回即驳回。

本流程审核节点直接在 BPM 设计器里指定角色（`ROLE` 候选策略），候选人由引擎按角色解析，后端零改动。两个模型由管理员在 BPM 后台人工创建、发布并启用，不入 `script/bpm` 版本化资产库、不使用全局自动部署。由于角色在模型内按角色 ID 绑定，新环境、新租户需在目标环境的 BPM 后台重新建模并绑定本环境的角色。

发布前按顺序完成：

1. 确认 V194 已在目标环境执行，`zsjos_material_type` 已存在租户级 `viral_account`、`viral_content` 两行，且素材审批分类 `zsjos_material` 由 `MaterialTenantInitializer` 在应用启动后已为该租户创建、启用。缺少任一前置的环境不得继续发布。
2. 确认目标环境存在启用的董事长角色，且该角色下至少有一名启用用户；该角色成员即审核节点的或签候选人。总监岗位补齐前不改绑，补齐后在第 4 步的模型里将审核节点角色从董事长改为总监并重新发布，不动流程结构与流程标识。
3. 在 Admin 进入“工作流程 → 流程管理 → 流程模型 → 新建模型”，选择 SIMPLE 设计器，为两个流程分别建模。流程标识分别填 `zsjos_viral_account_review`（名称“爆款账号拆解审核”）与 `zsjos_viral_content_review`（名称“爆款内容拆解审核”）；模型分类必须选当前租户已启用的 `zsjos_material`，不能留空或选其他分类，否则提交时按“流程不可用”失败。两个模型设为不可见、指定流程管理员。
4. 两个模型使用相同的三节点结构：发起人（编导） → 爆款审核（userTask） → 结束。审核节点参数：节点名称填“爆款审核”，不写“董事长/总监”以免误导；审批人来源选“角色”，绑定第 2 步的董事长角色；多人审批方式选“或签（一人通过或拒绝）”；审批意见必填打开；关闭“发起人自选审批人”。提交时 `startUserSelectAssignees` 保持为空，候选人由引擎按角色解析。
5. 表单类型选“业务表单”，`formCustomCreatePath` 与 `formCustomViewPath` 指向素材详情工作台路由。不新建静态流程表单字段；素材字段由动态模板版本决定，审核人在工作台查看素材内容。
6. 发布两个模型为新流程版本并保持启用。运行中的旧实例保留原定义并继续走完，不迁移、不重启、不改写在途实例。
7. 在“素材库 → 类型与模板”，把爆款账号类型的“素材审批流程”绑定 `zsjos_viral_account_review`，爆款内容类型绑定 `zsjos_viral_content_review`（对应前端 `materialType/index.vue` 的“素材审批流程”下拉）。未绑定流程的类型不能提交手工审批。
8. 用受控素材验证：编导提交一条爆款拆解草稿后，董事长角色成员产生或签待办；任一成员通过则该轮通过、素材版本生效；任一成员驳回则该轮驳回并写入必填审批意见；确认提交人不出现选审批人步骤。

本部署不改动后端代码、不新增数据库迁移、不修改 `script/bpm` 资产。回滚仅需在“类型与模板”解绑流程或在 BPM 停用模型，保留素材、素材版本、审批轮次及 BPM 历史。实际 BPM 建模、发布、启用与角色授权均需在目标环境单独确认，不包含在代码交付中。
