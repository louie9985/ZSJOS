## 人员展示协议

订单新增可空 JSON 字段 `repaired_actor_snapshot`，包含 version=1、tenantId、orderNo、repairKey、capturedAt 以及 ADMIN 类型的 submitter/可选 formalSales。补录来源固定为 order-actors-v312，时间是本次补录时间，不冒充原下单时姓名。该字段不是授权依据。

统一 SalesOrderSnapshot 读取器校验版本、修复来源、订单、租户及人员引用后使用修复快照覆盖人员展示，其余业务事实仍按原轮次规则读取；校验失败保留原历史展示。人员后来转移时，旧修复快照不能覆盖不同账号。没有轮次的两笔订单使用订单级修复快照，不创建审批轮次或 BPM 历史。

有当前轮次的目标定向修正人员对象。原始 imported_actor_snapshot 保留旧员工编号、姓名及来源，仅同步系统账号引用 orderUserId；完整原轮次保存在修复前镜像。不得把 LEGACY_EMPLOYEE 编号直接当成 ADMIN 编号。Admin 和 Workbench 沿用原 submitterUserName/formalSalesUserName 字段，不新增 API、菜单或权限。

## 运行顺序与保护

前置 MySQL 8、双台账 V311、LONGTEXT 修复备份字段。先部署并执行 SQL，再启动包含新 DO 字段的后端。旧后端忽略新增列，但无轮次补录展示须由新读取器提供。

1. `python script/sql/mysql/tools/order_actor_repair.py preflight`：纯只读核对固定清单；完成后改用 verify，不重新 freeze 历史证据。
2. `python script/sql/mysql/tools/order_actor_repair_test.py`：创建保留的隔离测试库，验证初次、重复、原值冲突、事务/台账失败、部分恢复、回退演练和空目标。
3. 保存私有前镜像和保护表摘要后，`python script/sql/mysql/tools/order_actor_repair.py apply`：逐语句失败即停止地运行 V312 原 SQL。
4. `python script/sql/mysql/tools/order_actor_repair.py verify`：核对目标账号、51 条轮次引用、15 个补录姓名及 UTF-8 HEX、23 个保留账号、客资不变与两张台账。

可用 `--database` 指定同一本地 MySQL 的隔离库。远程目标不能复用本地连接默认值。独立 SQL 可通过现有迁移 runner 或 UTF-8 fail-fast 客户端执行，禁止 --force。SQL 不依赖开发机私有旧库文件。

DDL 条件添加 JSON 列；若已存在则检查类型和可空性。DDL 可能隐式提交，数据失败后允许只留下新增列。数据、首次完整前后镜像、后置检查和双台账均在同一事务内提交，异常 ROLLBACK/RESIGNAL。固定目标缺失时跳过，空环境不造业务记录；存在但删除、状态、账号、轮次或原值不符时拒绝。

以数据库级命名锁和 SERIALIZABLE 事务防止竞争。首次 before/after 保存后不覆盖；重复执行不改业务行或版本。部分恢复必须整行匹配已留档 before 或 after；后续业务改动及残缺证据拒绝自动覆盖。完整镜像包含敏感字段，仅存本地修复备份及 Git 忽略目录，不提交。

## 恢复与验证边界

恢复前将每个目标整行与 after 镜像比较，全部匹配后按 before 恢复本次允许的字段，恢复顺序为订单业绩、审批轮次、订单；不写生成列，不删除订单，不自动删除修复证据或历史台账。保留可空列。后续使用旧版本的程序前须确认展示兼容性。真实回退另行审核，测试仅在隔离事务中演练并回滚演练本身。

V305/V306 原脚本不改写、不重放来覆盖本次合法结果。其完整后镜像验证可因合法后续修复报告差异，须按版本倒序理解。新增迁移不更改原 baseline；新装按现有 baseline 到 V312 顺序获取新增列。

Java 测试使用实际快照读取器验证空轮次、覆盖优先级、身份域、跨租户/跨订单拒绝、错误 JSON、归属变更及隔离库全部修复快照。两前端源码消费字段不变；登录后的真实页面验收与数据库验证分开记录。
