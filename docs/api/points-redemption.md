# 中世健积分兑换码

适用中世健租户 1。员工在工作台选择管理员维护的积分套餐，填写理由并上传附件；BPM Simple 完成审批后，后台为该申请生成一个兑换码，向申请人发送站内通知。允许配置同一审批人的连续节点自动去重，首次审批仍需人工操作。通知进入申请详情，兑换码由申请人主动查看。

## 启用步骤

1. 部署前执行 `script/sql/mysql/migrations/V296__points_redemption.sql`，前置版本为 V295；全新安装依照 `script/sql/mysql/bootstrap.sql` 和既有迁移顺序。V296 新增两张积分业务表、`infra_config.sensitive`、菜单按钮和通知规则，不创建套餐或角色授权。
2. 确认后端已有 `mybatis-plus.encryptor.password` 配置为受控的 16、24 或 32 字节 AES 密钥。它用于数据库加密，与外部平台的 `PARTNER_API_KEY` 是不同密钥；勿提交到源码。备份时应分别保护数据库和加密密钥。
3. 在现有「配置管理」中填写下表。API 密钥由管理员自行填写，不需要提供给开发人员。敏感配置须有原有配置编辑权限及 `infra:config:secret-update` 权限；输入框不回显，留空保存保留旧值。
4. 在「积分套餐」创建套餐，例如 5000 积分；积分范围 1–1,000,000，有效天数可留空表示永久有效。套餐是业务实体，使用套餐 API；系统不预置业务选项。
5. 使用 `script/bpm/zsjos_points_redemption/1.0.0/process-model.json` 作为 Simple 流程模板，流程标识固定为 `zsjos_points_redemption`。在设计器中选择实际董事长审批人，配置组织部门负责人，再发布流程。模板保留空的最终审批人，不能未经配置直接用于申请。
6. 在系统角色管理中按职责分配下表权限，并保留相应 BPM 待办查询、审批权限。迁移不会自动给任何角色授权。
7. 确认 Quartz 已运行后，在 Infra 定时任务页面建立处理器 `pointsIssuanceJob`，建议 Cron `0/10 * * * * ?`，参数留空、任务级重试次数为 `0`（发码业务已持久化重试），再确认任务已启用。创建任务会注册对应 Quartz 触发器，不需要对全部任务执行“同步”。确认配置后启用业务开关。部署脚本不会自动启动任务、重启服务或调用外部发码接口。
8. 使用真实申请人走一次申请、上级审批、董事长审批、通知、查看兑换码及状态同步，完成上线验收。

## 配置管理

| 配置键 | 默认值 / 约束 |
|---|---|
| `zsjos.points-redemption.base-url` | `https://zsj.nbility.ai/api/partner/v1` |
| `zsjos.points-redemption.api-key` | 空，敏感配置；填平台提供的 `PARTNER_API_KEY` |
| `zsjos.points-redemption.enabled` | `false`；准备完成后改为 `true` |
| `zsjos.points-redemption.timeout-seconds` | `30`；允许 5–60 秒 |
| `zsjos.points-redemption.max-attempts` | `5`；允许 1–10 次自动尝试 |

外部地址必须为 HTTPS，路径固定 `/api/partner/v1`，拒绝账号密码、查询参数和片段，不跟随重定向。服务端属性 `zsjos.points-redemption.allowed-origins` 默认仅允许 `https://zsj.nbility.ai`；更换平台来源需要运维审核并更新该白名单，不能仅通过配置页面把携带密钥的请求转向任意地址。

密钥加密入库；配置列表、详情、按键读取及导出不返回密钥或密文，只返回是否已配置。配置写入和兑换码查看不记录请求/响应正文。修改外部 API 密钥可直接在配置页面覆盖；更换数据库加密主密钥需要单独安排解密再加密迁移，不能直接替换，否则历史兑换码与密钥无法解密。

## 审批与业务约束

- 每份申请固定 `quantity=1`。申请理由必填，附件 1–10 份、每份最大 20MB；附件必须来自申请人自己的上传记录。
- 提交时保存套餐名称、积分、有效天数及附件名称快照；后续套餐修改不改变已提交申请。
- 套餐接口统一按积分从小到大、同积分按套餐 ID 从小到大返回；管理端和工作台的套餐列表、卡片及申请下拉框沿用接口顺序。员工选择仅返回启用套餐，管理列表包含停用套餐；申请记录列表仍按 ID 倒序返回。
- BPM 首个审批节点为申请人本部门负责人（策略 37，层级参数 `1`），最终节点为管理员选择的单个人员（策略 30）。最终人员由管理员确认是董事长，系统不通过角色名称推断身份。
- 流程必须是无条件串行审批，至少两个节点，单人处理（`approveMethod=1`）、无人审批时拒绝、禁止申请人自动跳过。允许在中间增加符合规则的人工节点；条件网关、跳过路径及多实例节点会阻止新申请。
- “更多设置 → 自动去重”可选择“不自动通过”或“仅针对连续审批的节点自动通过”（`autoApprovalType=2`）。同一指定审批人连续出现时，首次人工审批后，BPM 可自动通过后续连续节点；不要求关闭该去重设置。当前不支持“仅审批一次，后续重复的审批节点均自动通过”或其他自动审批方式。
- 允许人工审批节点启用“审批人超时未处理时 → 自动提醒”。仅接受 BPM 的任务超时定时提醒事件，且不能中断审批、连接额外流程入口/出口或带执行监听器；例如每 6 小时提醒、最多 3 次。超时自动同意、自动拒绝及其他边界事件仍不符合本流程的人工审批约束。
- 申请人不得审批自己的申请；部门负责人或最终审批人是本人时，申请会被拒绝并提示修正组织/流程配置。
- 固定流程版本及预期审批人。发码前核对每个节点：人工操作人须匹配该节点的审批人快照；连续去重节点须有 BPM 系统通过快照及对应的去重原因，且该任务历史流程版本已启用连续去重。自动节点的承办人必须与本节点、前一节点的审批人快照一致，完成时间不得早于前一节点，整段连续去重必须起于真实人工审批。缺节点、审批人变化、首节点自动通过或无法证明来源的自动通过均不发码。系统通过仍显示为系统处理，不补造人工操作人。转办、加签等可能改变审批人的操作不属于本流程支持范围。
- 拒绝和取消不发码；取消仅限申请人自己的审批中申请。重新申请产生新单，技术失败则必须重试原申请。
- 附件读取复用 Infra 文件服务和短期签名能力；底层存储若配置为公开读取，不应声称附件具备匿名访问隔离，应在正式使用前确认存储访问策略。

## 权限与页面

下列权限前缀均为 `zsjos:points-redemption:`；菜单来自服务端，接口另行鉴权。

| 后缀 | 权限与对象范围 |
|---|---|
| `query` | 工作台申请页及本人列表；详情另校验申请人、实际 BPM 参与人或管理权限 |
| `create` | 选择启用套餐、上传附件、提交申请 |
| `reveal` | 仅申请人主动读取已生成的兑换码；管理权限不授予查看他人明文码的能力 |
| `cancel` | 申请人取消自己的审批中申请 |
| `manage` | 管理列表及申请管理对象权限 |
| `retry` | 配合 `manage`，重试审批通过但发码失败的原申请 |
| `disable` | 配合 `manage`，调用平台作废兑换码 |
| `refresh` | 申请人、BPM 参与人或管理员主动同步平台状态 |
| `package` | 查看积分套餐页面/列表 |
| `package-save` | 新增、编辑、启停套餐 |

工作台入口 `/zsjos/points-redemption`，详情为 `?id=<内部申请ID>`；展示申请业务编号 `JF...`。该页菜单组件标记为既有 `zsjos-workbench`，Vue Admin 按既有规则过滤。套餐页 `/zsjos/points-packages` 在 React 和 Vue 共用同一 API。敏感配置页面在 Vue Admin 维护，员工工作台无独立密钥编辑实现。

两个积分页面同时注册到工作台 `RENDERABLE_APP_ROUTES`，PC 和手机共用这份运行时支持清单。仅在 `RouteHost` 接入组件不足以显示菜单；导航会过滤不在支持清单中的页面。该清单只声明前端支持的页面，不授予权限，入口仍取自服务端菜单和布局投影。

稳定错误码：`1090296001` 业务参数/状态错误，`1090296002` 对象无权限，`1090296003` 平台未配置或配置无效，`1090296004` 审批节点配置不符合要求，`1090296005` 流程未发布或已停用，`1090296006` 流程结构、自动审批或事件不支持，`1090296007` 指定审批人配置无效或与申请人相同。节点及审批人错误会提供具体原因；客户端继续展示服务端 `msg`。发码失败原因保存在申请状态中，区分密钥无效、原单参数冲突、平台限流/网络失败等。

超时提醒兼容修复需要重新构建并部署后端后生效；已发布且符合上述约束的流程可直接复用，不需要关闭提醒或仅为此重新发布。部署后的真实申请、审批及发码链路仍需单独验收。

## 发码可靠性与安全

### 审批进度和申请人催办

- `GET /admin-api/zsjos/points-redemption/approval?id=...`：沿用 query 或 bpm:task:query 功能权限及积分对象 read 权限，返回 availability、BPM progress、canUrge 和 nextUrgeAt（epoch 毫秒）。流程缺失/读取失败返回 UNAVAILABLE，不推断审批历史。
- `POST /admin-api/zsjos/points-redemption/urge?id=...`：请求体 `{ "idempotencyKey": "16至80位字母数字下划线或短横线" }`；功能权限 `zsjos:points-redemption:urge`，对象及业务层均限制申请本人，审批中且 BPM 运行时才能催办。
- 后端重新读取 BPM 当前任务及有效员工，按审批人去重，通过 System `publishDurable` 在同一事务内持久化通知。场景 `zsjos.points-redemption.approval_urged`，固定接收人为当前审批人，变量 requestNo、applicantName、taskName、taskId、processInstanceId、deepLink，不含兑换码。
- Redis 按租户/申请加锁，成功提交后 30 分钟冷却，成功重放键保留 1 天；同一网络重试沿用幂等键，System 通知事件另以稳定键去重。Redis 清理会重置冷却。未配置通知规则不显示成功；并发、冷却、流程结束、无有效审批人、通知未配置分别返回 1090296008—1090296012。
- 新接口为增量，现有 `/get`、列表和两端既有审批调用保持兼容。Workbench 增加时间线和催办操作，Vue Admin 原有页面不变。管理员在系统菜单配置催办按钮并通过角色管理授权，再配置上述通知场景的站内信/企业微信规则；代码交付不代表真实授权、通知渠道或部署已经完成。

BPM 结果事件只更新业务状态，不在审批事务内调用外部平台。Quartz 扫描持久化待发记录，Redis 互斥锁和短数据库事务防止并发发码；外部 HTTP 在数据库事务之外执行。提交幂等键绑定申请人及请求内容，数据库唯一约束兜底。

若审批已通过但持续显示“兑换码生成中”，先检查 `issueStatus`、`attempts` 和定时任务日志。`queued` 且尝试次数为 `0` 说明尚未进入外部调用，应核对 `pointsIssuanceJob` 是否存在、启用且具有运行中的 Quartz 触发器；处理器 Bean 存在不代表任务已注册。调度恢复后会扫描原申请，无需重新申请或重新审批。当前 Spring Boot 4 的 Quartz 自动配置类为 `org.springframework.boot.quartz.autoconfigure.QuartzAutoConfiguration`，不要根据旧版包名的排除项断言调度器已关闭；应以实际启动状态和调度器心跳为准。

每份申请保存永久唯一的 `orderId`。首次准备发码时固定平台地址及有效期（上海时区、秒精度）；每次尝试都先按原 `orderId` 查询，未找到才创建，网络超时不能换订单重发。返回积分、数量、状态和有效期必须匹配申请。原单参数冲突需人工核查，重试不能修改参数规避冲突。

自动重试采用退避并尊重 `Retry-After`，达到次数上限转失败。生成成功后先加密保存，再以持久化通知事件通知申请人；通知失败不会再次生成码。通知内容不含兑换码；详情与列表不含明文，查看后关闭页面清除组件中的明文。Redis 按当前用户限流：申请每分钟 10 次、查看兑换码 30 次、状态同步 10 次。

平台协议只提供 Bearer 认证，本系统未假设平台支持请求签名或回调。平台没有回调，兑换状态通过主动同步查询；平台明确已使用的码不能作废。HTTP 错误仅保留受控错误码，不记录密钥、兑换码或完整响应。

## 数据库与验证记录

V296 仅增量定义本功能对象和元数据，未写入真实密钥、套餐、申请、角色授权。MySQL DDL 会隐式提交；失败时保留已创建结构，检查实际结构与两本版本台账，再重复执行。版本只在必要结构和元数据校验成功后写入；不能以存在版本号替代结构检查。回退以关闭新申请/暂停任务并保留历史数据为原则，不删除码或审批记录。

`schema/core.sql` 与 `00-bootstrap-schema.sql` 保持同字节。受控测试入口为 `script/sql/mysql/tools/test_points_redemption.py`，覆盖首次、重复、部分建表恢复、前置缺失、版本写入失败、已有版本但缺结构及错误字段类型；`--fresh` 验证全新安装链，`--inspect-local` 只读，`--sync-local` 仅用于已确认的本地 `ruoyi-vue-pro` 开发库。

开发验证使用隔离的模拟 API，没有调用真实平台。正式环境的真实鉴权、BPM 审批到 Quartz、外部发码、通知投递及文件存储访问策略仍须按启用步骤验收。

## 积分套餐管理表格与删除

工作台积分套餐使用 BusinessTable 完整模式。套餐 API 返回完整管理列表，在该列表上按名称搜索、按名称/积分/有效期/状态排序、按启用状态筛选并分页，支持调整每页数量。新增和编辑继续使用 package-save 接口。

新增 `DELETE /admin-api/zsjos/points-redemption/package-delete?id=...`，要求 `zsjos:points-redemption:package-delete`，并在服务层校验 points-package 对象的 delete 权限。事务内锁定当前租户套餐后逻辑删除；与创建申请共用套餐行锁，历史申请快照不变。

上线前由管理员在系统菜单管理的“积分套餐”页面下添加“删除积分套餐”按钮，权限标识为 `zsjos:points-redemption:package-delete`，再通过角色管理按需分配。此代码变更不修改现有授权，也不自动同步数据库菜单。未配置/分配时删除入口不可见，接口拒绝未授权操作。现有 Admin 调用接口保持不变。
