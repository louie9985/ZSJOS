# 客资流转记录 API

## 查询接口

```text
GET /admin-api/zsjos/lead/{leadId}/flow-history
```

`leadId` 是路由和对象关系使用的内部主键，不作为用户可见“客资编号”。客资详情仍以
`leadNo` 展示业务编号。调用者必须同时满足：

- 功能权限 `zsjos:lead-detail:flow-read`；
- 当前租户；
- 现有统一 Lead 对象读取关系。

功能权限不扩大客资对象范围。跨租户、无关用户或只有菜单权限的请求不能读取记录。

### 身份展示与脱敏

新版操作使用发生时的姓名快照，再按当前查看人实时脱敏；旧记录继续解析当前姓名，不修改既有历史。详情域统一使用
Lead 身份投影规则：自动/普通派单且已归属、提交人与负责人不同的客资，负责人查看时仅隐藏提交人身份，
员工提交人查看时仅隐藏负责人身份；判定人、待接销售、回收来源、操作人及原/新负责人仅在其员工 ID
等于当前查看人的对方时显示中文脱敏值，第三方查看人不脱敏。合作方身份与员工用户使用独立 ID 命名空间；拥有
`zsjos:lead:query-all` 或负责人所属部门主管权限的用户显示完整员工名称。系统操作显示“系统”，
无法解析的员工显示“未知账号”，兼职名称同样按该上下文投影。指定派单不启用相互脱敏。

## 响应字段

新版 `lead_submitter_supplemented` 节点从 `append_v1` 事件快照展示本次补充备注。
旧版节点的 `before.remark` 不代表当次填写内容，不展示为当次备注。存在旧版补充事件时，
“客资提交”节点不再以当前 Lead 备注冒充首次备注；有依据的旧文本统一在详情 `remarkHistory` 中展示为历史备注。
新版补充节点的操作人显示为“提交人”，来源由快照的主体类型确定；Partner 操作不会因 ADMIN 用户 ID 为空而被标为系统操作。

接口返回按 `occurredAt DESC`、原始数值记录 ID 倒序排列的数组：

| 字段 | 说明 |
|---|---|
| `id` | 稳定投影键，格式为 `lead:{id}`、`event:{id}`、`assignment:{id}` 或 `public-sea-pool:{id}`；仅用于列表稳定性 |
| `occurredAt` | 实际发生时间 |
| `businessObject` | 客资、客资分配、公海、客资跟进或客资申诉 |
| `flowNode` | 稳定事件码映射的中文节点 |
| `source` | 员工工作台、兼职端、系统任务、自动分配、指定派单或公海处理 |
| `operator` | 新版使用操作人姓名快照；旧版解析当前 System/Partner 姓名；无法解析时为“未知账号” |
| `fromOwner` / `toOwner` | 原归属和新归属销售名称 |
| `leadStatusBefore` / `leadStatusAfter` | 客资状态变化；无变化时为空 |
| `assignmentStatusBefore` / `assignmentStatusAfter` | 分配状态变化；无变化时为空 |
| `reason` | 来源记录保存的业务原因；判无效优先使用事件中的原因标签快照 |
| `remark` | 来源记录保存的说明或备注；提交、有效性判定和跟进记录按已有持久化事实映射 |
| `attachments` | 来源事件保存的证据引用 |

客资或分配状态变化仅记录一侧状态时，缺失的一侧保持为空，已知的一侧正常返回中文名称；
不会补造缺失状态，也不会因空状态导致整份流转历史查询失败。两侧状态相同或均为空时不展示状态变化。

`attachments` 包含 `infraFileId`、`originalName`、`contentType`、`previewUrl`、
`previewable` 和 `available`。只有图片和 PDF 会签发 10 分钟预览地址；接口不提供下载动作。
无法签名的引用返回 `available=false`，其他文件返回 `previewable=false`，前端分别显示
“附件不可用”和“暂不支持预览”。

## 合并与去重

### 历史代码中文展示

历史 `lead_valid/lead_invalid` 显示“判定有效/判定无效”，`lead_pending_follow/lead_following` 显示“待跟进/跟进中”；状态变更、状态修复、申诉中、关闭、成交确认及历史协助/投诉节点均由服务端映射中文。历史复合状态（待分配、抢单池、超时待处理、回收待处理、成交待审核等）仅根据原事件两侧状态展示，不从当前客资状态反推。

分配 `other` 显示“其他分配记录”；仅当原因为精确的 `legacy assignment history baseline` 时显示“历史分配初始记录”，不把导入基线描述为一次真实派单。原因开头的 `legacy-assignment-log-{数字}`、`legacy-claim-{数字}` 导入标记分别显示“历史分配记录”“历史抢单记录”，后续业务原因保留。转换仅作用于响应，原始数据库记录不变；普通备注、字典快照和姓名不做英文替换。

未识别事件、分配、公海类型使用相应的“历史类型未识别”中文提示，内部代码不作为标题返回。新版状态快照遇到未知系统枚举时保存“历史标签未记录”，不以代码冒充标签；已有快照和管理员维护标签不重新解析。

兼职昵称仅用于 H5 排行榜；流转记录仍使用业务姓名。销售负责人查看兼职姓名时沿用服务端脱敏，即使指定派单也脱敏；完整身份授权和持久化姓名不变。见[姓名与昵称契约](partner-profile-nickname.md)。

- Lead 的 `submittedAt`（缺失时使用创建时间）投影为“客资提交”。
- `zsjos_business_event` 投影判定、挂起、恢复、申诉、跟进和关联分配事件。
- `zsjos_lead_assignment_history` 投影派单、接单、拒单、超时、抢单、转派、回收和释放。
- `zsjos_lead_public_sea_pool_event` 投影公海进入、协作人分配/变更和退出。
- 业务事件的 `relatedObjectRefs.assignmentHistoryId` 指向分配历史时，只保留业务事件投影。

合并只读取现有持久化事实，不回填或猜测缺失历史。现有来源表没有统一的操作人或销售
姓名快照，因此删除账号后无法保证还原历史姓名；接口不会用显示名称推断身份或来源。
历史 `lead_appeal_overturned` 事件即使保存的是申诉审核状态，也按该稳定事件语义投影为
客资“无效 → 有效”；提交申诉和维持原判不投影客资状态变化。历史 `converted` 客资状态码
兼容显示为“有效”，但不会改写原事件记录。

## 页签契约

详情响应的 `visibleTabs` 仅在权限检查通过时包含 `flow-history`。Workbench 可接受
`/zsjos/leads/manage?leadId={内部客资ID}&tab=flow-history`，但必须再次消费服务端
`visibleTabs`；无权限时回退 `overview`。现有业务通知仍进入申诉、投诉、跟进或概览，
不会自动改为流转记录页签。

## 新操作快照 v1

仅补全新版代码生效后的操作。旧记录不回填、不改写；旧客资发生的新操作正常记录。以 `related_object_refs.flowSnapshot.version=1` 区分新旧，不依赖日期。新记录保存当时的操作人名称和字典/实体标签，再按当前详情权限脱敏。旧记录仍可能因账号删除而无法还原姓名。

既有 API 路径、数组返回值和旧字段保持兼容，新增：

| 字段 | 含义 |
|---|---|
| `snapshotVersion` | 新版为 1，旧版为空 |
| `operationResult` | 完成、审核中、成交生效、驳回、终止等结果 |
| `changes` | 实际改变字段的字段名、中文标签、before/after |
| `changes[].before/after.state` | VALUE、EMPTY、UNRECORDED；分别显示历史值、原值为空/已清空、历史未记录 |
| `relatedType/relatedId/relatedNo` | 经关联业务读取校验的引用；内部 ID 不作为可见客资编号 |

存储复用 `zsjos_business_event`，新增 `lead_flow_operation` 事件。`flowSnapshot` 保存变化、身份、操作结果和被合并记录键；`flowRemark` 保存当次备注；`evidence_refs` 保存当次附件引用。细分业务事件不删除，查询按明确引用合并为一张操作卡片。

### 操作覆盖

- 客资提交、派单、自拓自动跟进及判有效；重复联系方式激活提醒；有明确客资关联的重复复核结果。未形成客资的复核记录仍在原业务查看。
- 接单、拒单、抢单、本人/主管转派、回收、释放抢单池、超时重新分配和自动重试。
- 判有效、判无效、主管直接改判、自动挂起、主管恢复及新的判定安排。
- 新增跟进、阶段/类别/跟进时间变化、提交人补充、协助请求及回复。
- 公海进入、分配/更换/清除协作人、退出；与归属或成交操作联动时合并。
- 申诉每轮提交及处理结果、投诉及处理结果、向提交人反馈。
- 转派申请提交、通过、驳回、取消、失效和实际归属变化。
- 明确关联客资的成交/复购提交、修订重提、终止和审批最终结果。中间审批步骤没有业务状态变化时不单列；订单金额、产品等表单差异不写入客资时间线。

关键变化包含姓名、联系方式、地区、类别、意向产品、状态、负责人/待接人员、身份、销售阶段、跟进时间、判定轮次/截止时间、挂起时间、判定说明、关闭字段、备注、来源/提供方、公海状态和协作人。技术版本号、更新时间等不显示为业务修改。当前没有客资关闭/重开命令，本次不新增该业务能力。

### 一致性、权限与交付

命令拦截器通过既有 TransactionTemplate 加入业务事务，批处理按每条记录显式捕获。历史写入失败回滚业务修改；业务失败不生成成功事件；原业务幂等重放不新增事件。新提交只在成功创建路径记录，不给旧提交重放补造历史。自动回调无法取得真实办理人时显示系统。

查询继续校验功能权限和 Lead 对象范围。快照中的员工/兼职原始标识不直接返回，姓名沿用现有身份脱敏。结果与客资变化可在时间线看到；原因、备注、附件及单据引用需要通过原业务读取校验。订单沿用客资订单历史的同 Person 契约；反馈同时校验逐条接收关系；复核使用现有复核对象权限。转派申请没有独立详情读取契约时只显示操作结果和客资变化，不开放表单或链接。查询不更新最近活动时间。

Workbench 展示主要状态变化，展开查看全部字段变化，业务保存后刷新记录。管理端当前没有流转历史消费者；各端写入 API 保持兼容。无需数据库迁移、角色授权或旧数据修复。后端和 Workbench 都需部署后才能生效；直接 SQL 不会自动产生业务事件。浏览器夹具 `frontend/workbench/test/lead-flow-history*` 只使用模拟传输。
