# 学生交付服务关闭与恢复

学生交付中心以 `serviceRelationId` 操作单条课程服务。教学关闭与共享关系 `status` 分开保存：
`teaching_closed=true` 时，教学列表及详情展示 `closed / 已关闭`，新媒体仍消费原关系状态。
`teaching_delivery` 继续表示是否参与教学，关闭不能把它改为 false。订单、报名履约、退款和新媒体审批不随本操作取消。

## 操作与权限

接口前缀为 `/admin-api/zsjos/student/service/{relationId}`，返回标准 `CommonResult`。

| 接口 | 功能权限 | 对象范围 |
| --- | --- | --- |
| GET `/lifecycle` | `zsjos:student:query-my` | 当前服务可读 |
| POST `/close` | `zsjos:student-service:close` | 当前教学负责人，服务中且未关闭 |
| GET `/restore-targets` | `zsjos:student-service:restore` | 原负责人所在部门在配置的管理范围内 |
| POST `/restore` | `zsjos:student-service:restore` | 原服务管理范围与目标班管理范围同时满足 |

关闭、恢复请求均含 `reason`（必填，最多500字）、`version`、`idempotencyKey`。恢复可传 `targetClassId`，
不传时使用最近一次关闭前班级。目标必须是有效普通或未确定考期服务中班级，其班主任通过现有资格校验。
主管恢复弹窗默认原班；原班无效时必须重新选择。恢复时负责人随目标班主任，不重置接收及交付阶段的历史事实。
System 数据范围的 SELF 不扩为本人部门；新增按钮不产生数据范围，不自动授权任何真实角色。

`lifecycle` 返回 `closed/previousClassId/closedAt/availableActions/history`。历史保存每轮操作原因、时间、操作人及目标班级、负责人快照。
列表默认排除关闭；明确筛选 `serviceStatus=closed` 或进入异常结业班可查询历史。详情、旧教学聚合接口和子资源保留原数据范围。
已关闭服务禁止教学联系、阶段推进、改考试日期、普通调班、内部资料与档案维护；恢复入口单独授权。

## 异常结业系统班

班型 `classKind` 为 `NORMAL/PENDING/UNSCHEDULED/EXCEPTION`。`systemClass` 为兼容字段，不能单独作为待分班判据。
待分班继续全租户唯一、无固定班主任；异常结业按规划师唯一、有固定负责人，不附带待分班的特殊读取范围。

启动及每60秒使用 System 公共 API 与既有规划师资格规则幂等补建空班；关闭命令也保证目标班存在。
系统班随有效规划师的姓名、部门更新；人员停用不删除班级与历史。班级并发唯一约束由数据库保证。
异常结业班不绑定产品、考期，不允许人工创建、编辑、删除或结课。报名分班与普通调班后端拒绝此班型，
前端也不提供其作为安排目标。关闭和恢复是专用转入、转出命令。

## 任务、审批与事务

关闭取消当前服务的首联、学习计划、普通联系、教学阶段和首联协助待办，保留任务历史；移出待办计数与提醒扫描。
联系延期与教学调班的业务申请及 BPM 实例同步取消；不删除审批历史。恢复不重启任务或审批，也不生成替代任务。

关闭、恢复以服务关系行锁、版本及幂等事件控制并发。教学申请回调统一先锁服务、再锁申请；关闭先标记申请取消，再调用 BPM 公共取消 API。
业务与 Flowable 参与同一 Spring 数据源事务，取消或后续步骤失败必须整体回滚，不通过 afterCommit 忽略失败。
迟到回调不得修改关闭服务的任务截止时间或班级；已取消申请重复回调无操作。

恢复过的服务在没有当前待办时，可按原阶段主动提交首联或学习计划，继续使用对应表单与校验。
只有 `teaching_restored=true` 且与当前阶段一致才允许首联／计划无任务提交，不能通过缺省 taskId 绕过普通服务的原任务要求。
日常联系沿用无任务主动联系；提交后填写下次时间才生成后续任务。恢复命令本身不生成任何待办。

## 2026-10-24：关闭服务通知交付主管

成功关闭当前课程服务后，通过 System `NotifyBusinessEventApi` 在同一事务中写入持久化通知队列。
场景为 `zsjos.student.service_closed`，业务主体为 `student_service`、业务 ID 为当前 `serviceRelationId`；
通知业务入口复用 Workbench 与 Admin 已有的课程服务深链，不新增审批或待办。

交付主管沿用现有教学提醒的部门负责人来源：关闭时学习规划师所属部门的 `leaderUserId`。
接收人必须启用、不是规划师本人，并持有学员页权限和该课程服务的对象读取权；不按角色名称推断，也不向上级部门或其他员工兜底。
事件记录当次主管 ID、服务姓名快照、课程快照、学习规划师姓名、关闭原因及时间，异步发送不重新解析当前姓名或组织关系。
姓名或课程快照缺失时保持缺失，不从 Person／Lead 补造历史含义。

每轮关闭采用服务 ID 与关闭后版本号组成幂等事件键；客户端重试不会重复发通知，恢复后再次关闭产生新通知。
关闭失败、BPM 取消失败或历史登记失败不发布关闭通知；队列写入失败会回滚关闭状态、任务和历史。
恢复服务不发送本场景通知；消息描述已发生的关闭事实，即使随后恢复也不改写旧通知。

V349 在 V348 双台账之后新增一个站内模板和租户1默认启用的站内规则，接收人角色为 `delivery_supervisor`，
操作为 `business_detail`。迁移重放保留管理员已有模板、渠道、指定接收人和禁用状态，不补发历史关闭通知，不授予权限。
其他渠道可通过现有 System 通知配置启用。主管缺失或不符合条件时不阻止业务关闭，已入队的通知按 System 缺少接收人失败机制保留诊断及重试；
没有启用规则时遵循 System 不投递的既有配置语义。迁移执行、部署和真实账号送达验收分别进行。
