# 学生详情读取范围

## 2026-10-22：独立查看全部权限

学员管理新增 `zsjos:student:query-all`（查看全部学员），与页面查询权限 `zsjos:student:query-my` 累积使用。未显式指定读取人员时，该权限将课程服务列表、搜索、总数、详情及兼容的旧学员查询扩大到当前租户全部符合教学交付条件的服务；仍保留租户、逻辑删除、教学参与、服务状态和用户筛选条件。它不使用角色名称、部门名称或固定用户判断，也不扩大新媒体学员权限。

班级管理另有 `zsjos:delivery-class:query-all`（查看全部班级），只扩大班级及班内名单读取，不自动授予学员详情全读；学员全读也不自动授予班级页面、班级筛选接口或班级全读。没有新增权限时继续遵循下文严格本人/部门规则。已有租户读取范围选择器的显式 `SELF`/`USER` 保持人员约束，不能因拥有新增全读权限而被忽略。

两端依据实际功能权限和后端对象动作控制入口与请求。学员联系操作及调班入口使用当前服务的 `availableActions`；班级编辑、结课及整理使用班级动作。全读本身不授予接收、联系、修改资料、调班或关闭/恢复服务权。档案维护保持已有契约：独立档案查看/维护权限与精确服务可见性累积，不能只凭全读执行维护。无相关读取功能权限时，不请求客资详情、联系记录或班级筛选等附属接口。

V348 仅新增这两个可配置按钮及双版本台账，不分配、继承或重置角色授权。管理员通过系统角色管理选择所需权限；应用先具备新权限语义，再配合两端动作投影使用。新增读取能力与真实账号验收、部署结果分别记录。

## 2026-10-19：严格读取数据范围

学员管理保留 `zsjos:delivery-class:query` 与 `zsjos:delivery-class:query-managed` 的历史查询入口兼容，但功能权限不产生部门数据授权。管理读取使用 System `getDeptDataPermission` 返回的全部/部门集合；`self=true` 只保留本人关系，不能转换为本人所在部门。多角色范围由 System 合并，空部门集合不扩为本部门，范围解析异常直接失败。

本人负责及既有个人协作关系继续独立生效；部门范围只按服务 owner 所属部门增加读取权，不按同部门其他人的协作关系扩大范围。新课程服务分页/搜索、旧学员分页/详情、student/student-service 对象权限及联系上下文/记录使用一致的严格读取边界。同一学员的范围外课程不可通过可见课程、旧通知或服务深链读取。

班级管理分页、筛选上下文及班级详情采用相同的严格部门读取规则，并保留本人班主任关系。系统待分班的独立 `query-managed` 读取例外继续有效；仅普通 query 不获得该例外，显式 SELF/USER 不附加待分班。列表可见不授予跟进、修改资料、分配和调班权。现有命令范围解析与状态/归属校验保持独立。

本次不修改角色授权、服务归属、数据库结构或历史记录。Admin 与 Workbench 共用既有接口和响应结构；源码测试、只读 SQL/浏览器样本和部署后的真实账号验收分别记录。

2026-10-19：考试与证书信息按当前服务独立维护，无需先提交收集表；原报名收集资料仍按冻结表单展示。详见 [学员信息收集与档案](student-information-collection.md)。

2026-10-18：新增“学员档案”标签页，查看 `zsjos:student-archive:read` 和维护 `zsjos:student-archive:update` 分别配置；维护同时要求查看权限与当前服务本身可读。档案绑定当前报名任务、Person 和订单商品，原始答案不可变，内部修订单独记录。Workbench visibleTabs 和 Admin 权限状态控制入口，后端独立校验功能与对象权限；敏感读取、图片和导出保留独立权限。详见 student-information-collection.md。

2026-10-16：具有 `query-managed` 权限的主管还可读取租户真实系统待分班内的 active/paused/completed 课程服务，无需服务已有负责人。课程服务分页与详情、兼容的旧学员分页与详情、student/student-service 对象读取权限保持同一边界；普通用户和显式 SELF/USER 查询不增加此范围。范围外正式班课程不因同学员另一条待分班服务可读而开放。读取权限不附带接收、联系或修改资料的执行权限。

`GET /admin-api/zsjos/student/my/{personId}` 和 `GET /admin-api/zsjos/student/my/by-service/{relationId}` 使用既有学生查询权限及对象权限。

具有管理读取入口权限（兼容 `zsjos:delivery-class:query` 和 `DeliveryClassService.PERMISSION_QUERY_MANAGED`）的用户，详情按学生列表同一严格部门范围、服务 owner 集合及本人既有协作关系读取。除上文新增学员全读权限外，全范围来自服务端数据范围；空部门集合不包含同部门其他人。交付主管另持有 `zsjos:delivery-class:direct-transfer` 时，可按现有命令规则发起主管直接调班；查询权限不授予接收、联系、分配或学员资料修改操作。普通用户保持本人负责及既有协作查询规则。

同一学生不同课程分别受服务关系范围限制。按服务关系读取必须确认指定关系本身可见，不能借另一条可见关系读取范围外课程；响应只聚合可见关系。范围解析失败不降级为全量查询。

Admin 的 `RegistrationApi.getMyStudent` 与 Workbench 的 `api.myStudent` 消费相同接口；响应结构未改变。按服务关系入口的对象权限同步支持已有管理读取范围。

验证覆盖：普通负责人/协作者、部门范围内/外、全范围、空范围、历史服务、同学生跨范围课程、范围解析异常，以及管理读取不授予写操作。

页面详情还会读取 `/zsjos/student/service/{relationId}/contact-context` 和 `/contact-records`。这两个子资源的服务内部校验复用同一 `student-service` 管理读取权限；仅通过主详情接口不能作为整个详情页验证成功的依据。原有负责人命令校验保持不变。

## 2026-10-21：学员服务姓名快照

本节替代 2026-10-20 的实时订单姓名规则。课程服务分页、详情、班级学员以及服务级关键词、姓名排序、高级筛选 `person.name` 使用 `zsjos_service_relation.student_name_snapshot`。读取时不回退订单或 Person/Lead；后续核实回填服务快照即可恢复显示。

按 Person 汇总的学员/媒体学员列表与详情，仍选择当前可见服务中最早订单对应的服务快照（订单 createTime 升序、空时间最后、订单 id 升序）。同订单多服务按服务 createTime 升序、空时间最后、服务 id 升序；无可用订单时按相同服务顺序选择。不会跨可见范围取姓名，也不跳过空快照取其他服务姓名。具体服务详情始终使用指定服务的快照。汇总关键词匹配投影姓名、联系方式、学员编号、客资编号和订单编号；不匹配 Person 主档姓名或被其他订单服务快照遮蔽的姓名。姓名排序使用投影姓名。

新订单履约创建服务时复制订单 studentName，来源为 `order_creation`；独立导入保存本次录入姓名，来源为 `independent_entry`。已有服务重放导入不覆盖姓名。订单更名、解绑或主档更名不自动更新快照。空快照保留缺失提示；修改联系方式接口不提供姓名编辑，不变更订单或主档。

V337 前置 V336 双台账，按编号执行后再部署应用。新增可空姓名与来源字段，仅将租户 1 未删除服务关联的同租户未删除订单非空姓名复制到未初始化快照，来源为 `order_migration`，表示迁移时采集而非历史原始姓名。已存在快照或来源不覆盖。无订单、订单不可用、订单姓名为空的记录不回填；55 条无订单服务最初暂缓；2026-10-21 用户随后明确授权从当前主档回填，本地已补录 55 条，来源 `person_current_repair`，表示本次取主档姓名，不认定为历史创建姓名。迁移不修改订单/主档/权限，DDL 不能事务回滚；失败检查字段与双台账后重放，应用回退保留扩展列及值。

本次修复使用 `script/sql/mysql/tools/student_name_backfill.py`：`prepare` 生成仓库外私有恢复计划，`apply-local --plan <path> --sha256 <hash>` 仅执行精确计划。范围限定租户 1、未删除、无订单、姓名和来源均未初始化且同租户有效主档姓名非空的服务；已有快照不覆盖。写入前锁定并核对来源/目标，事务失败整批回滚，保留原更新时间、版本及其他业务字段。重复执行原计划为零变更，UTF-8 连接与姓名 HEX 校验必需。恢复时只能按原计划逐条核对当前值仍为本次 after-image 后恢复原快照/来源，不能覆盖后续人工修改。私有计划含姓名，不入库源码、不输出日志；迁移 V337、版本台账和主档均不修改。

Admin 与 Workbench 响应字段仍为顶层 `name`、服务条目 `studentName`，只改变其来源。新编导/运营指派通知使用服务快照；已生成通知、订单审批快照、收集表答案保持不变。

## 2026-10-20：新媒体学员与教学交付边界

`zsjos_service_relation.teaching_delivery` 明确控制是否纳入教学交付，数据库默认 true；现有记录保持纳入，不根据订单、负责人、角色名称或补录批次自动改标。页面不增加关闭按钮，也不新增通用修改标记接口。直接生成编导/运营学员时，操作者先获得用户对该批数据是否纳入教学交付的确认，再明确写入 true/false。

false 的服务关系保留 Person、服务 ID、编导/运营、资料预审、定位访谈、定位卡、账号和相关历史；没有教学班级或教学订单亦可执行原有新媒体业务。新媒体的列表、详情、服务期归类、兼职绑定、负责人分配和账号/定位操作继续沿用原有对象授权。字段只区分教学参与，不替代媒体状态、服务期或角色权限。

学生交付中心的课程服务列表/搜索/总数、详情、旧 Person 聚合接口以及班级学员/人数/项目范围只读取 true 的关系；同一 Person 另有正常教学服务时，该教学服务继续显示。旧通知或按服务 ID 请求不会绕过这条边界。仅新媒体关系禁止接收、教学联系、教学阶段推进、考试日期修改及调班；新媒体业务的 student-service/read 上下文和编导/运营指派保留。Admin 与 Workbench 共用后端规则和原有响应，无前端交互变更。

V336 为增量兼容升级，前置 V335 的两张版本台账；bootstrap/schema 同步默认字段，应用先升级数据库再部署。迁移只扩容字段并登记台账，不修改历史业务归类或角色授权；重放保留人工 false 与原始台账，DDL 部分失败需检查字段与台账后重放。历史误入交付的候选记录必须单独核对和授权，不按缺订单推断。

## 2026-10-21：关闭服务历史

已关闭教学服务继续按原负责人及严格管理范围读取；默认教学列表排除，明确状态／异常结业班筛选可查。异常结业系统班不继承待分班的特殊可见性。维护命令与档案写入独立拒绝已关闭服务，恢复须有专用权限及源／目标管理范围。这里的关闭不修改教学参与标记，不替代上文 teaching_delivery 边界，详见 [关闭恢复契约](teaching-service-close-restore.md)。


2026-10-22：媒体学员和兼容的 Person 聚合学员接口的关键词候选 SQL 纳入同租户、未删除服务的 `student_name_snapshot`。候选仅减少读取量，最终仍以已授权服务投影再次匹配；未增加 Person/Lead/订单姓名回退，也不扩大当前教学服务分页接口的读取范围。

教学关闭服务只有共享状态仍为 `active` 时才投影恢复操作；历史全读不绕过该条件。跨服务并发复用相同幂等键命中 `uk_teaching_event_key` 时返回既有 KEY_CONFLICT，当前命令全部回滚；其他唯一约束错误不伪装为幂等冲突。

WorkBench 学员详情中的关联客资历史沿用 `LeadManagementController.get` 的 `student:query-my` 或 `lead:query` 查询契约，不额外要求客资管理页权限。仅真实服务关联的 Lead 才请求详情，后端对象读取权限继续独立生效；拒绝时不展示未授权内容。
