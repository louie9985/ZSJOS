# 中仕健编导与运营业务通知

## 范围与渠道

编导、运营、拍剪、内容审核、账号交付和工作计划均通过 System 场景、租户规则、模板和站内信／企微 outbox 发送。
V269 补站内信默认配置，并从业务站内模板／规则生成缺失的企微配置；不修改租户渠道开关、个人推送偏好、权限或历史消息，不增加短信配置。
企微与站内信独立投递，规则配齐不等于已送达；企微仍需启用渠道、有效应用配置、账号绑定和个人推送许可。
已有规则（包括管理员停用的规则）优先，不能因补全覆盖其接收人、渠道或状态。
新协作通知冻结操作时真实业务责任人，去重并排除操作人；旧场景保留其既有接收语义。

| 业务变化 | 接收人／行为 |
| --- | --- |
| 指派编导 | 新编导沿用报名履约通知；更换时原编导收到交接消息 |
| 指派运营 | 新运营收到指派消息；更换时原运营收到交接消息，多个课程关系去重 |
| 预约访谈 | 服务负责人、编导、运营（排除操作人） |
| 访谈时间提醒 | 编导、运营；默认提前 60 分钟，由租户规则配置 |
| 完成访谈 | 服务负责人、编导、运营（排除操作人） |
| 提交定位、运营退回 | 沿用运营待复核、编导退回通知 |
| 运营复核通过、生成学员链接 | 通知另一协作方；链接仍由运营手工分享，不把安全令牌写入通知 |
| 学员同意／要求修改 | 沿用编导和运营结果通知；同意后仍等待运营凭证 |
| 凭证提交、定位正式生效 | 通知另一协作方；重复提交不重复通知 |
| 开始修订、账号应用／换版 | 通知另一协作方；应用未改变提交时不发变更通知 |
| 创建账号、状态维护 | 通知另一协作方；维护无实际变化不发消息 |
| 内容待验收组批 | 通知内容所属运营，进入批审准备；不恢复旧单条审批入口 |
| 内容批次提交／逐条结论／编导完成或退回／终审结果 | 使用内容批审场景的编导、运营、实际终审任务接收人、提交人角色配置 |
| 审核超时 | 从 BPM 当前任务创建时间计算，默认逾期 1440 分钟，通知当前节点实际任务负责人 |
| 登记内容发布 | 通知账号另一协作方 |
| 拍剪与通用工单 | 拍剪指定派单、关系场景自动派单、公共池、接单、拒接、待验收、返工、完成、终止、撤回使用既有业务事件；自动派单从 `new_media_operator_filming_editor` 关系场景的有效目标中选择当前未完成拍剪工单最少者 |
| 阶段交付到期 | 责任编导；默认 due 0，模板声明 stageCode |
| 阶段交付完成 | 账号另一协作方 |
| 阶段交付延期 | 沿用当前即时延期流程，通知其主管；不新增审批流程 |
| 周期诊断到期 | 编导；已有默认主管逾期规则继续有效，两类规则分别投递 |
| 提交初始／周期诊断或修订 | 账号另一协作方 |
| 工作计划任务 | 分派、调整、取消、提醒、逾期、汇报、确认结果和计划待总结沿用对应业务角色 |

草稿保存、附件暂存、模板维护和查看详情不产生协作通知。账号换绑和反馈处理继续使用现有通知链路。
旧 IP 定位审批场景仅供在途流程兼容，不恢复已退役入口。

## 可靠性和权限

- 新提醒每分钟按租户扫描，并服从维护模式；访谈只扫描 active/accepted 且处于定位访谈阶段的关系。
- 访谈提前提醒不补发已经过去的预约。审核提醒只面向尚未结束的实际 BPM 任务，使用冻结的节点 key。
- 同任务、同规则的事件键稳定，由 System outbox 去重；业务状态变化与通知发布共用业务事务。
- 媒体诊断与阶段交付分别发布所有适用规则，再记录阶段；不会只发最紧急规则而吞掉另一个接收人或渠道。
- MediaNotifySceneProvider 严格按 assignee/supervisor 角色选取接收人；指定用户仍由 System 规则处理。
- 缺少主管不会自动猜测替代主管。历史失败消息不自动补发，需另行审核补偿范围。

## 消费端

Workbench 的消息弹窗、铃铛和消息中心共用动作解析器。内容批审、通用工单、工作计划先读取真实业务 API
校验访问，再打开指定记录；列表第一页没有目标记录时仍按指定 ID 加载。
诊断、阶段交付、服务关系和未绑定账号的定位卡通过媒体学员 target 接口解析；目标接口重新验证关系／对象权限。
定位卡返回附加的 serviceRelationId，确保进入正确课程服务。消息中不存在可执行任意 URL。
用户将规则设为 message_detail 时只开消息详情；对象不可访问或请求失败则回退消息详情并提示。
Vue Admin 继续显示同一 System 消息契约，未支持的员工业务动作回退消息详情，不复制 React 员工流程。

## 部署与验证边界

V269__director_operator_notifications.sql 在 V268 后、匹配后端部署窗口中执行；为 59 个编导运营场景及 5 个既有提现场景补全缺失站内模板和规则。
提现场景与兼职企微跳转边界见 [业务通知契约](system-business-notifications.md#withdrawal-and-partner-wecom-destinations)。
站内默认值保留管理员规则，唯一特殊情况是在未修改、启用的 V216 主管默认规则之外补一条编导 due 默认规则。
企微补全范围包含全部有效业务站内模板，以及非删除租户中尚无任何有效企微规则的业务场景，
因此也覆盖 V177 之后新增的客资反馈等场景。先生成模板，再同时复制该场景的全部站内规则，保留
接收角色、指定用户、动作、提醒阶段／时间和启停状态；同场景多条提醒不会互相覆盖。
已有企微规则（包括停用、自定义规则）的场景不自动追加；同编码模板不覆盖。模板沿用 V177 的
`_WECOM` 编码及长编码缩短规则。新租户继续复用 System 默认规则初始化能力，匹配企微模板后生成双渠道默认规则。
管理员后续修改任一渠道不会实时同步另一个渠道，需分别维护。回退仅停用本次新建规则。

既有 V220 模板无需改写：后端补声明 stageCode 即可满足其变量契约。新增租户使用同一组场景默认值。

测试命令：`python3 script/sql/mysql/tools/test_director_operator_notifications.py`，使用隔离 MySQL 容器，
检查默认与自定义租户、停用规则／模板保留、多接收人／多提醒规则、双渠道配置一致性、关联、中文 HEX、重复执行和版本记录。
本脚本不授权共享 test 库写入。实际同步前需确认目标库、租户和新增规则影响，并保留受影响配置备份。
回退时仅停用本次新增规则，保留已产生的消息及业务历史；不删除业务数据、不撤销角色授权。

企微现复用 System 持久化 outbox，按收件人保存投递结果并跳过已成功者。明确的临时拒绝可重试；超时、响应无法解析或发送中进程中断标记为 `uncertain`，不自动重发。提醒任务的 `publishConfirmed` 成功表示企微已持久化入队，不代表已送达；运维可通过 `GET /system/notify-rule/delivery-page` 查询本租户投递结果，需已有 `system:notify-rule:query` 权限。详细状态、重试和保留期见 [业务通知契约](system-business-notifications.md)。
