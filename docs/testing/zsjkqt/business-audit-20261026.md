## 需要明确的业务口径与流程风险

1. **事假/调休改“出勤”不会自动扣源假期小时。** 只有事假与调休之间的特定转换自动调整小时；年假、加班小时也一直沿用源汇总。日历可全天出勤、事假汇总仍 8 小时。现有测试明确要求源小时独立，并有“人工修改，汇总数据待核对”提示。本轮保留该契约。若目标是异常改正常后汇总同步清零，需要批准改变这一契约，并处理源月总数与逐日明细不一致的情况。
2. **正式汇总表续改与企业微信原月报不同。** 正式表缺原始时长，日状态修改不重算汇总；月参数只更新应出勤、计薪字段。人工汇总覆盖也优先于自动计算。这能避免覆盖已核实结果，但必须把“日历修正”和“汇总核对”作为两步，不能承诺所有入口自动联动。
3. **“陪产假”“产检假”“带薪”未计入实出勤。** 病假、婚假、产假、年假、调休等却计入；陪产假和产检假也未计入产假天数。现有 API 契约要求保留独立假别且不擅自改公式，需要明确它们是独立计薪项、实出勤项还是只展示。测试记录当前结果，不代表认可该口径。
4. **异常清单不是全部修订流水。** Java 导出要求系统或最终状态中存在字面值“异常”；缺卡→出勤、事假→调休、迟到→出勤等即使有备注，也不会进入异常清单。页面异常数又只看最终“异常”，已解决的地点异常可以页面为 0、导出仍有记录。建议明确区分“待处理异常”和“人工修订记录”；目前不能拿异常清单审计所有改正常操作。
5. **确认不是审批锁。** 日状态或汇总再编辑时，通用 `updateEmployee` 不自动撤销 confirmed；导出按 enabled 筛选，不要求所有人 confirmed。若“已确认”代表最终审核，修改后应撤销确认，并决定未确认能否正式导出；若仅是浏览进度则应说明。未擅自增加导出限制。
6. **异常恢复依赖原始打卡依据与可定位时长。** 上午/下午按真实班次小时权重，不是固定各 0.5 天；迟到当前计全天出勤但可产生处罚，早退扣分钟；休息、带薪休息和独立加班不自动增加实出勤。空白源日期即使选休息日也保留空白。这里有既有测试约束，不能仅凭名称或“异常变正常”统一成一天。
