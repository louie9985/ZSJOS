# 积分兑换码工作台

默认展示服务端当前可申请的积分套餐，不表示个人积分余额或已持有的兑换权益。卡片名称、积分、有效期及顺序来自现有套餐 API，图案通过共享 avatar-kit 按套餐 ID 稳定生成，适配工作台主题。

页面按积分套餐、我的申请、申请管理分类。套餐读取需要现有 create 或 package 权限，只有 query 权限时进入我的申请；管理页签需要 manage 权限。操作继续使用既有权限及服务端对象授权，不新增角色推断或静态权限数据。

卡片入口预选套餐，申请弹窗可切换。附件复用 DeferredAttachmentPicker，支持文件选择、截图粘贴、预览、移除；提交时通过原积分上传 API 上传，再创建申请。至少 1 份、最多 10 份、每份不超过 20MB，文件类型沿用后端限制。部分上传失败时保留成功文件，重新提交仅重试失败文件；申请创建重试沿用幂等键。

详情按套餐状态、申请信息、理由、附件、兑换信息及操作区排列。历史套餐名称、积分和有效期使用申请快照。附件使用 AttachmentCard，通过原详情 API 重新获取有权访问的附件，支持预览、下载及失败重试。兑换码仅在主动查看后显示，关闭详情时清除。

桌面卡片自适应列数，窄屏单列，弹窗详情自适应单/双列。套餐与列表分别处理加载、空、错误、重试及未授权状态。

验证入口：`test/points-redemption.html`、`python test/points-redemption-browser.py`（隔离模拟 API，非真实发码验收）。生产业务不使用预览示例数据。

## 审批进度与催办

详情独立加载审批流程，展示总体状态、当前审批人、节点状态、到达/处理时间及审批意见。通过积分业务授权后的 `/approval` 读取 BPM 公共进度投影；失败时允许单独重试，不影响附件和申请信息。

催办仅对申请本人、配置了 `zsjos:points-redemption:urge` 权限、流程仍运行且有待分配到用户的任务时开放。后端提交时重新读取当前待办，只通知有效的当前审批人，并按人去重；不使用启动时的审批人快照。30 分钟冷却由带租户与申请维度的 Redis 控制，页面展示下次可催办时间。网络失败重试沿用幂等键，通知通过 System 持久化事件发出。

启用要求：后端部署后，由管理员在积分兑换码菜单下新增“催办”按钮，权限标识为 `zsjos:points-redemption:urge`，通过角色管理分配。消息规则配置场景“积分申请审批催办”（`zsjos.points-redemption.approval_urged`），启用站内信或企业微信持久化渠道；建议模板“{applicantName} 催办积分申请 {requestNo}，请处理 {taskName}”，动作选择业务详情。接收人使用事件固定的当前审批人。规则缺失/停用时返回明确错误，不扣成功冷却。

本次不自动新增真实角色授权或修改通知配置，也不触发真实催办。Redis 数据丢失会重置冷却；通知事件自身使用稳定键去重。提示“催办已提交”表示事件已持久化，不等于通知渠道已送达。工作台消息会先校验该任务当前可处理，再跳转审批；已处理/转办的任务打开消息详情。
